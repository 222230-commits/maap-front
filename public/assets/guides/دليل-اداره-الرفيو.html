دليل إداره الرفيو

شرح كامل لكل الـ Endpoints الخاصة بتقييم المنتجات والتعليق عليها، مع كل شكل طلب واستجابة، وكل فخ برمجي يجب الانتباه له قبل البدء بالتنفيذ. هذا الدليل موجّه لمن يبني الفرونت إند لأول مرة على هذا الـ API.

نظرة عامة واختيار الأداة

الميزةالأداة المقترحةالسبب
شاشة تصفح تعليقات/تقييمات المنتج (Scroll + Pagination) Flutter قائمة طويلة قابلة للتمرير داخل تطبيق المشتري على الموبايل، تحتاج تحميل تدريجي (per_page)
شاشة تقييم بالنجوم + كتابة تعليق (تدفق متسلسل مع شروط تفعيل) Flutter تفاعل تسلسلي بسيط (نجوم ثم نص) داخل تطبيق موبايل، وليس جدول بيانات معقد يحتاج لوحة تحكم
حذف/تعديل تعليق المستخدم نفسه (can_manage) Flutter إجراء سريع (زر/قائمة منسدلة) داخل نفس شاشة العرض على الموبايل، لا يحتاج واجهة إدارية منفصلة
i كل المسارات هنا مخصّصة للمشتري (Buyer) داخل تطبيق الموبايل، لذلك لا يوجد سبب لاستخدام Angular/React هنا؛ هذه الأدوات تناسب أكثر لوحات تحكم التاجر أو الإدارة التي لا تظهر في هذه المجموعة من المسارات.

حالة المستخدم لمنتج معيّن

GET /Buyer/review/products/{product}/user-review

هذا هو أول Endpoint يجب استدعاؤه عند فتح شاشة التقييم، لأنه يخبرك بكل الحالات التي تحتاجها لبناء الواجهة الصحيحة قبل أن يبدأ المستخدم بأي تفاعل.

مثال الاستجابة (مستخدم اشترى ولم يقيّم بعد)
{
  "message": "تم جلب حالة تقييم المستخدم بنجاح.",
  "has_purchased": true,
  "has_reviewed": false,
  "has_commented": false,
  "review": null
}
مثال الاستجابة (مستخدم قيّم وعلّق بالفعل)
{
  "message": "تم جلب حالة تقييم المستخدم بنجاح.",
  "has_purchased": true,
  "has_reviewed": true,
  "has_commented": true,
  "review": {
    "id": "uuid",
    "rating": 4,
    "comment": "منتج ممتاز",
    "created_at_human": "منذ ساعتين",
    "created_at": "2026-07-30 10:12:00",
    "updated_at_human": "منذ ساعتين",
    "updated_at": "2026-07-30 10:12:00",
    "is_edited": false,
    "buyer": { "id": "uuid", "name": "أحمد", "avatar": null },
    "purchased_variants": [
      { "product_name": "قميص قطني", "color": "أزرق", "size": "L" }
    ],
    "can_manage": true
  }
}
الحقلماذا يعني للفرونت
has_purchasedإن كانت false: لا تعرض واجهة التقييم إطلاقاً، اعرض رسالة "اشترِ المنتج أولاً"
has_reviewedإن كانت false: اعرض نجوم التقييم فقط، وحقل التعليق يكون معطّلاً (disabled)
has_commentedtrue فقط إذا كان نص التعليق غير فارغ فعلياً (وليس مجرد وجود تقييم)
reviewnull إن لم يوجد تقييم بعد، وإلا كائن كامل بنفس شكل عناصر القوائم
⚠ هذا المسار يتطلب تسجيل الدخول دائماً (موضوع ضمن مجموعة مسارات محمية بـ auth:sanctum). لم يعد الكود يحتوي أي معالجة خاصة لحالة "زائر غير مسجّل دخول" — أي طلب بدون توكن صالح سيُرفض مباشرة بخطأ 401 قبل الوصول للدالة أصلاً. لا تستدعِ هذا المسار من شاشة عامة يمكن للزوار فتحها بدون تسجيل دخول، وتعامل معه كمسار يتطلب مستخدماً مسجلاً دائماً.

قائمة التعليقات النصية للمنتج

GET /Buyer/review/products/comments/{product}?per_page=10

يعيد فقط التقييمات التي تحتوي على comment نصي غير فارغ (تجاهل التقييمات بالنجوم فقط بدون نص).

مثال الاستجابة (مختصر — الشكل الكامل paginated)
{
  "message": "تم جلب التعليقات بنجاح.",
  "data": [
    {
      "id": "uuid",
      "rating": 5,
      "comment": "جودة ممتازة وسريع",
      "created_at_human": "منذ يوم",
      "created_at": "2026-07-30 08:00:00",
      "updated_at_human": "منذ ساعة",
      "updated_at": "2026-07-31 09:00:00",
      "is_edited": true,
      "buyer": { "id": "uuid", "name": "سارة", "avatar": "https://..." },
      "purchased_variants": [
        { "product_name": "حذاء رياضي", "color": "أسود", "size": "42" }
      ],
      "can_manage": false
    }
  ],
  "links": { "first": "...", "last": "...", "prev": null, "next": "..." },
  "meta": { "current_page": 1, "last_page": 3, "per_page": 10, "total": 25 }
}
✓ حقل جديد is_edited يخبرك مباشرة إن كان المستخدم قد عدّل تعليقه بعد إنشائه لأول مرة (يقارن created_at مع updated_at في الباك إند)، بدل أن تقارنهما بنفسك من الفرونت. استخدمه لعرض شارة صغيرة "(معدَّل)" بجانب التعليق، واستخدم updated_at_human لعرض وقت آخر تعديل بدل وقت الإنشاء عند الحاجة.
⚠ purchased_variants لا يمثل كل مشتريات هذا العميل من هذا المنتج عبر كل الطلبات التاريخية، بل فقط عناصر أحدث طلب مكتمل ارتبط به التقييم. إذا اشترى نفس المستخدم المنتج مرة أخرى بلون/مقاس مختلف لاحقاً، سيتغيّر محتوى هذا الحقل تلقائياً في المرة القادمة التي يُحدَّث فيها التقييم، حتى لو بقي نص التعليق نفسه. لا تفترض ثباته كتأريخ كامل للشراء.
⚠ هذا المسار ومسار "كل التقييمات" أدناه يعيدان نفس شكل الكائن بالضبط (نفس بنية JSON)، لكنهما مصدران منفصلان تماماً في الباك إند: هذا يعرض التعليقات فقط، والآخر يعرض كل التقييمات (بتعليق أو بدونه). لا تشارك نتائج الكاش بينهما — تعامل معهما كقائمتين مختلفتين تماماً حتى لو تشابه الشكل.

قائمة كل التقييمات (بالنجوم مع أو بدون تعليق)

GET /Buyer/review/products/rates/{product}?per_page=10

نفس شكل استجابة قائمة التعليقات تماماً، لكن دون فلترة — أي يشمل كل من قيّم المنتج بالنجوم سواء كتب تعليقاً أم لا. أصبحت الاستجابة الآن تحتوي أيضاً حقل summary إضافي مع الإحصائيات الجاهزة.

مثال الاستجابة (مختصر)
{
  "message": "تم جلب التقييمات بنجاح.",
  "summary": {
    "average_rating": 4.2,
    "total_reviews": 128,
    "rating_distribution": {
      "5": 70,
      "4": 30,
      "3": 15,
      "2": 8,
      "1": 5
    }
  },
  "data": [ "... نفس شكل عناصر ReviewResource كما في قائمة التعليقات أعلاه ..." ],
  "links": { "...": "..." },
  "meta": { "current_page": 1, "last_page": 13, "per_page": 10, "total": 128 }
}
الحقلماذا يعني للفرونت
summary.average_ratingرقم عشري بخانة عشرية واحدة (مثال 4.2) — جاهز للعرض مباشرة دون حساب يدوي
summary.total_reviewsإجمالي كل من قيّم المنتج بالنجوم (بتعليق أو بدونه) — نفس معنى meta.total في هذا المسار تحديداً
summary.rating_distributionعدد التقييمات لكل نجمة من 1 إلى 5 — استخدمه مباشرة لرسم أشرطة التوزيع (Bar لكل نجمة) دون تجميع يدوي
✓ حقل summary يُحسب مرة واحدة لكامل المنتج بغض النظر عن رقم الصفحة الحالية — اعرضه مرة واحدة أعلى الشاشة (متوسط + توزيع)، ولا تُعِد حسابه أو تغييره عند التنقل بين الصفحات (Pagination) لأن قيمته ثابتة لكل صفحات نفس المنتج.
⚠ summary يظهر فقط في هذا المسار (rates/{product}) — لا يظهر في مسار التعليقات (comments/{product}) ولا في user-review. إن احتجت عرض متوسط التقييم في أي شاشة أخرى غير شاشة "كل التقييمات"، يجب استدعاء هذا المسار تحديداً للحصول عليه، ولا تفترض وجوده تلقائياً في استجابات المسارات الأخرى.

إرسال تقييم بالنجوم (إنشاء أو تحديث)

POST /Buyer/review/products/{product}/rate
الطلب (Request Body)
{
  "rating": 4
}
الحقلالقاعدة
ratingمطلوب، رقم صحيح، بين 1 و 5
استجابة النجاح — 200
{
  "message": "تم حفظ التقييم بنجاح.",
  "data": {
    "id": "uuid",
    "product_id": "uuid",
    "buyer_id": "uuid",
    "rating": 4,
    "comment": null,
    "order_item_id": "uuid",
    "created_at": "2026-08-01T10:00:00.000000Z",
    "updated_at": "2026-08-01T10:00:00.000000Z"
  }
}
استجابة الخطأ — 403 (المستخدم هو صاحب المنتج)
{
  "error_code": "OWN_PRODUCT_REVIEW_FORBIDDEN",
  "error": "عملية غير مصرح بها: لا يمكنك تقييم منتج تابع لمتجرك."
}
استجابة الخطأ — 403 (لا يوجد شراء مكتمل)
{
  "error_code": "PURCHASE_REQUIRED",
  "error": "عفواً، يجب عليك شراء وتجربة هذا المنتج أولاً لتتمكن من إعطاء رأيك فيه."
}
⚠ لاحظ أن شكل data هنا يختلف تماماً عن شكله في قوائم التعليقات/التقييمات أو في user-review. هنا هو الكائن الخام من قاعدة البيانات (بدون buyer، بدون purchased_variants، بدون can_manage، وبدون created_at_human، updated_at_human، أو is_edited الجديدين). كل الحقول المحسوبة الموجودة في ReviewResource غير موجودة هنا لأنها تُبنى فقط داخل الـ Resource وليست جزءاً من الكائن الخام. لا تحاول استخدام نفس دالة العرض (Parsing) على استجابة هذا المسار كما تفعل مع القوائم — ستحصل على حقول ناقصة. الأفضل عملياً: بعد نجاح الطلب، أعد استدعاء user-review لتحديث الشاشة بالشكل الكامل والموحّد.
✓ هذا المسار هو Upsert: نفس الطلب يعمل لإنشاء تقييم جديد أو لتعديل تقييم قديم لنفس المنتج — لا يوجد مسار منفصل للتعديل، فقط أرسل نفس الطلب مرة أخرى بقيمة نجوم جديدة.

إرسال أو تعديل التعليق النصي

POST /Buyer/review/products/{product}/comment
الطلب (Request Body)
{
  "comment": "منتج رائع وسريع التوصيل"
}
الحقلالقاعدة
commentاختياري (nullable)، نص، بحد أقصى 500 حرف — إرسال null يمسح التعليق
استجابة النجاح — 200
{
  "message": "تم حفظ التعليق بنجاح.",
  "data": { "id": "uuid", "rating": 4, "comment": "منتج رائع وسريع التوصيل", "...": "نفس شكل data في POST rate" }
}
استجابة الخطأ — 422 (لا يوجد تقييم مسبق)
{
  "error": "يجب تقييم المنتج بالنجوم أولاً قبل كتابة تعليق."
}
⚠ هذا هو الشرط الذي يفرض ترتيب الخطوات: لا يمكن إرسال تعليق قبل إرسال تقييم بالنجوم أولاً (لأن حقل rating في قاعدة البيانات لا يقبل قيمة فارغة). لذلك يجب أن يعتمد الفرونت على حقل has_reviewed القادم من user-review لتعطيل صندوق كتابة التعليق تماماً حتى يُنجز المستخدم خطوة النجوم أولاً، بدل أن يعتمد على محاولة الإرسال ثم عرض رسالة خطأ 422.

حذف التعليق فقط (مع الاحتفاظ بالتقييم)

DELETE /Buyer/review/products/{product}/delete-comment

لا يحتاج جسم طلب (Body). يمسح نص التعليق فقط ويُبقي على تقييم النجوم كما هو.

استجابة النجاح — 200
{
  "message": "تم مسح التعليق بنجاح والاحتفاظ بالتقييم."
}
استجابة الخطأ — 404 (لا يوجد تعليق لحذفه)
{
  "error": "لا يوجد تعليق مسبق لحذفه."
}
⚠ استجابة النجاح هنا لا تحتوي حقل data إطلاقاً — فقط رسالة نصية. الباك إند لن يرسل لك الكائن المحدَّث، لذلك على الفرونت تحديث الحالة محلياً بنفسه (اجعل قيمة comment تساوي null في الواجهة مباشرة بعد نجاح الطلب) بدل انتظار بيانات من الاستجابة.
⚠ هذا الإجراء غير قابل للتراجع — بمجرد حذف نص التعليق يُفقد نهائياً، ولا توجد نسخة محفوظة يمكن استرجاعها. اعرض تأكيداً واضحاً للمستخدم (Dialog "هل أنت متأكد؟") قبل استدعاء هذا المسار، ولا تربطه بزر عادي بلا تأكيد.

جدول ملخّص لكل الأخطاء المتوقعة

الكوديظهر فيالمعنىماذا يفعل الفرونت
401 كل المسارات لا يوجد توكن صالح للمستخدم أعد المستخدم لشاشة تسجيل الدخول
403 — OWN_PRODUCT_REVIEW_FORBIDDEN POST rate المستخدم هو صاحب المتجر لهذا المنتج أخفِ زر التقييم كلياً لهذه الحالة إن أمكن معرفتها مسبقاً، أو اعرض الرسالة كما هي
403 — PURCHASE_REQUIRED POST rate لا يوجد طلب مكتمل لهذا المنتج اعرض رسالة "اشترِ المنتج أولاً" — ويفضَّل منعها مسبقاً عبر has_purchased
422 (تحقق Laravel القياسي) POST rate / POST comment rating خارج نطاق 1-5، أو comment أطول من 500 حرف اعرض رسالة تحقق تحت الحقل المعني مباشرة قبل الإرسال إن أمكن (تحقق محلي مسبق)
422 (رسالة مخصصة) POST comment لا يوجد تقييم مسبق للمستخدم على هذا المنتج لا يجب أن يحدث إن اعتمدت على has_reviewed لتعطيل الحقل — اعتبره حماية إضافية فقط
404 DELETE delete-comment لا يوجد تعليق نصي لحذفه أصلاً عطّل زر الحذف إن كان has_commented يساوي false
404 (Route Model Binding) كل المسارات المحتوية على {product} رقم المنتج غير موجود اعرض شاشة "المنتج غير موجود" العامة

نصائح عملية لتفادي الاحتكاك مع الباك إند

  1. استدعِ user-review دائماً عند فتح شاشة التقييم أولاً، واستخدم حقوله الثلاثة (has_purchased, has_reviewed, has_commented) للتحكم بالحالة المرئية للشاشة، بدلاً من الاعتماد على أخطاء 403/422 كوسيلة للتحقق.
  2. لا تعتمد على شكل data في استجابة POST rate أو POST comment لعرض بيانات كاملة (اسم المشتري، الصورة، المتغيرات المشتراة) — أعد جلب user-review بعد كل عملية ناجحة للحصول على الشكل الكامل والموحّد.
  3. عامل قائمتي "التعليقات" و"كل التقييمات" كمصدرين منفصلين تماماً من ناحية التخزين المؤقت (Cache/State) رغم تطابق شكل عناصرهما.
  4. اعرض المتوسط وتوزيع النجوم من حقل summary الجاهز داخل استجابة rates/{product} مباشرة — لا داعي لحسابهما يدوياً بجلب كل الصفحات، لكن تذكّر أن هذا الحقل موجود في هذا المسار فقط.
  5. اعرض تأكيداً صريحاً قبل استدعاء حذف التعليق لأنه إجراء نهائي لا يمكن التراجع عنه.
  6. بعد نجاح حذف التعليق، حدّث حالة الشاشة محلياً (اجعل comment = null) لأن الاستجابة لا تُعيد بيانات التقييم المحدّثة.
  7. راقب دائماً حقل can_manage ضمن كل عنصر تقييم في القوائم لتحديد إظهار أزرار التعديل/الحذف بجانب تعليقات المستخدم الحالي فقط.

ملاحظة مقترحة لفريق الباك إند

✓ تم فعلاً إضافة حقل summary (المتوسط، الإجمالي، توزيع النجوم) في GET rates/{product}، وتم حذف الفرع الميت الخاص بحالة "زائر غير مسجّل دخول" من userReview بعد أن كان غير قابل للوصول أصلاً. النقطتان اللتان ذُكرتا سابقاً في هذا القسم أصبحتا محلولتين، وما تبقى أدناه ملاحظة جديدة تستحق المراجعة.
⚠ داخل rateindex، استعلام حساب summary يستخدم DB::table('product_reviews') بدون بادئة السكيما app.، بينما كل الاستعلامات الأخرى في نفس الملف (وموديل ProductReview نفسه عبر protected $table = 'app.product_reviews') تلتزم دائماً بتحديد app. صراحةً (مثل app.order_items وapp.orders). إن لم يكن search_path الافتراضي لقاعدة البيانات يتضمن سكيما app، فقد يعيد هذا الاستعلام صفراً في كل حقول summary بصمت (بدون خطأ ظاهر) بدل القيم الصحيحة، أو يفشل إن لم يوجد جدول بنفس الاسم في سكيما أخرى. يُنصح بتوحيدها لتصبح DB::table('app.product_reviews') مثل بقية الاستعلامات، أو تأكيد أن إعداد الاتصال بقاعدة البيانات يضبط search_path تلقائياً على app.
