دليل ربط الفرونت إند بنظام إدارة الإعلانات

هذا الدليل يشرح بالتفصيل كل مسار (Route) متعلق بالإعلانات في المشروع: مسارات لوحة تحكم الإدارة (Admin) التي يُفترض بناؤها بـ Angular، ومسار عرض الإعلانات للمشتري الذي يُفترض استهلاكه من تطبيق Flutter. لكل مسار: شكل الطلب، كل أشكال الاستجابة الممكنة، منطق العمل الخفي، والفخاخ التي يجب الانتباه لها قبل البدء بالتطوير.

نظرة عامة واختيار الأداة

الميزةالأداة المقترحةالسبب
لوحة إدارة الإعلانات (جدول، إنشاء، تعديل، حذف، رفع صورة، إعادة ترتيب) Angular واجهة إدارية تحتوي جدولاً به فلترة حسب المكان (position)، نماذج (Forms) متعددة الحقول مع Validation، ومودالات تعديل/حذف — هذا نمط لوحات التحكم الكلاسيكي الذي يناسب Angular Reactive Forms وخدمات HTTP المهيكلة.
عرض الإعلانات للمستخدم النهائي (بانرات، بوب-أب) Flutter استهلاك بسيط لمسار واحد (GET /ads) وعرضه كسلايدر/بانر داخل تطبيق الموبايل — تجربة بصرية بسيطة وسلسة داخل التطبيق، لا تحتاج نماذج معقّدة.
ملاحظة عامة على المصادقة جميع مسارات لوحة الإدارة محمية بـ auth:sanctum + Middleware اسمه IsAdmin، أي يجب إرسال Bearer Token لحساب أدمن مع كل طلب. أما مسار المشتري GET /ads فهو عام تماماً بدون تسجيل دخول (معرّف خارج مجموعة auth:sanctum في ملف الراوتس)، فيمكن لتطبيق Flutter استدعاءه فوراً دون أي توكن.
نطاق كل واجهة (مهم) كل مسارات /admin/* (بما فيها كل مسارات هذا الدليل تحت "لوحة الإدارة") مخصصة لواجهة Angular فقط ولا يجب استهلاكها من تطبيق Flutter إطلاقاً — فهي تتطلب صلاحية أدمن ولا معنى لها داخل تطبيق المشتري. أما مسار المشتري العام GET /ads فهو المسار الوحيد في هذا الدليل المشترك بين الاثنين، ويمكن استهلاكه من Angular (لو وُجدت واجهة عرض عامة فيها) ومن Flutter معاً بنفس الشكل تماماً.

2. إنشاء بيانات الإعلان (بدون صورة)

POST /admin/ads/store Bearer Token (Admin)
مثال طلب (Request Body — JSON)
{
  "shop_id": null,
  "title": "عرض الصيف الكبير",
  "target_type": "external",
  "target_id": null,
  "target_url": "https://example.com/summer-sale",
  "position": "home_main_banner",
  "sort_order": 2,
  "is_active": true,
  "start_date": "2026-08-10",
  "end_date": "2026-08-31"
}
الحقلالقاعدةملاحظة
shop_idnullable | uuid | يجب أن يكون موجوداً فعلاً في جدول shops—
titlerequired | نص | حتى 255 حرف—
target_typerequired | واحدة من: external, product, shop, categoryلا يوجد ربط تلقائي بين هذه القيمة وبين target_id/target_url (انظر التحذير أدناه)
target_idnullable | uuid فقط (بدون فحص وجوده فعلياً)لا يتحقق الباك إند أن هذا الـ id موجود فعلاً في جدول المنتجات/المتاجر/التصنيفات
target_urlnullable | رابط صالح—
positionnullable | نص حرلا قائمة مسموحة محددة في الباك إند — أي نص يُقبل
sort_ordernullable | رقم صحيح ≥ 1الباك إند يعيد حسابه تلقائياً (انظر أدناه)
is_activeboolean—
start_datenullable | تاريخإن لم يُرسل، يُضبط تلقائياً على الآن
end_datenullable | تاريخ | يجب أن يكون بعد أو يساوي start_date—
فخ: لا تحقق من تطابق target_type مع target_id / target_url الحقول target_id و target_url غير مرتبطة منطقياً بـ target_type في الباك إند إطلاقاً — يمكن نظرياً حفظ target_type = "product" بدون أي target_id، أو target_type = "external" بدون target_url، وسيُقبل الطلب بنجاح. على واجهة Angular فرض هذا الترابط بنفسها (مثال: عند اختيار target_type = external أظهر حقل الرابط كإلزامي، وعند اختيار product/shop/category أظهر حقل اختيار target_id كإلزامي وأخفِ حقل الرابط).
فخ: منطق sort_order تلقائي ومختلف حسب وجود position
  • إذا لم تُرسل position إطلاقاً: يُحفظ sort_order كما أُرسل من الفرونت حرفياً بدون أي تعديل أو تحقق من تعارضه مع إعلانات أخرى.
  • إذا أُرسلت position: الباك إند يتجاهل الرقم الذي أرسلتَه إن كان أكبر من (أعلى ترتيب حالي + 1) ويضعه تلقائياً في النهاية.
  • إذا أرسلتَ رقماً ضمن التسلسل الحالي (مثلاً تريد وضعه رقم 2 وهناك 3 إعلانات)، سيُزاح كل ما هو ≥ 2 خطوة واحدة للأسفل تلقائياً.
لا تحاول حساب sort_order يدوياً في الفرونت عندما توجد position — أرسل الرقم الذي يريده المستخدم فقط ودع الباك إند يعيد ترتيب البقية، ثم اعتمد على القيمة المُعادة في الاستجابة كمصدر الحقيقة.
استجابة 201 — نجاح
{
  "success": true,
  "message": "تم إنشاء بيانات الإعلان بنجاح، يرجى رفع الصورة الآن",
  "data": { "id": "b1f5c2b0-....", "title": "...", "image_url": null, "sort_order": 2, "...": "..." }
}
استجابة 422 — خطأ تحقق (شكل Laravel الافتراضي، ليس {success:false})
{
  "message": "The title field is required. (and 1 more error)",
  "errors": {
    "title": ["The title field is required."],
    "target_type": ["The selected target type is invalid."]
  }
}
فخ: شكل استجابة الخطأ مختلف عن شكل استجابة النجاح استجابات النجاح تتبع الصيغة {success, message, data}، لكن أخطاء 422 (فشل Validation) تأتي بصيغة Laravel القياسية {message, errors} بدون حقل success إطلاقاً. لا تعتمد Angular Interceptor على وجود success: false لاكتشاف كل الأخطاء — تحقق من الـ HTTP Status Code (422) واقرأ errors مباشرة لعرضها تحت كل حقل في الفورم.

POST /admin/ads/{id}/image Bearer Token (Admin)

POST /admin/ads/b1f5c2b0-.../image

image: (ملف) jpeg / png / jpg / webp، الحد الأقصى 5120 كيلوبايت (5 ميجا)
استجابة 200 — نجاح
{
  "success": true,
  "message": "تم رفع الصورة بنجاح",
  "data": {
    "id": "b1f5c2b0-....",
    "image_url": "https://rdvvlvabfisrvesoltrd.supabase.co/storage/v1/object/public/ads/newfile.jpg",
    "...": "..."
  }
}
ميزة مهمة: لا تبني رابط الصورة بنفسك الحقل image_url في كل استجابات القراءة (index / show / store / update / uploadImage) هو دائماً رابط كامل وجاهز للعرض المباشر (رابط Supabase عام)، لأن الموديل يحوّله تلقائياً عبر Accessor في الباك إند. لا داعي لأي منطق في Angular/Flutter لتركيب الرابط أو إضافة دومين — استخدم القيمة كما هي في وسم الصورة مباشرة.
فخ: استبدال الصورة يحذف القديمة نهائياً رفع صورة جديدة لإعلان لديه صورة سابقة يحذف الملف القديم من التخزين السحابي (Supabase) فوراً وبشكل غير قابل للتراجع قبل حفظ الجديدة. إن فشل رفع الملف الجديد لأي سبب بعد نجاح حذف القديم، سيبقى الإعلان بلا صورة مؤقتاً. يُفضّل إظهار تأكيد بسيط ("سيتم استبدال الصورة الحالية") قبل السماح باختيار ملف جديد لإعلان يملك صورة بالفعل.

GET /admin/ads/{id}/show Bearer Token (Admin)
استجابة 200
{ "success": true, "data": { "id": "...", "title": "...", "...": "..." } }
استجابة 404 — id غير موجود
{ "message": "No query results for model [App\\Models\\Ad] b1f5c2b0-..." }
فخ: 404 لا يتبع صيغة {success:false} عند إرسال id غير موجود، Laravel يرمي استثناءً افتراضياً برسالة تقنية بالإنجليزية وليست بصيغة المشروع المعتادة. لا تعرض هذه الرسالة كما هي للمستخدم — اعرض رسالة عامة مثل "الإعلان غير موجود أو تم حذفه" عند استقبال 404 من أي مسار من مسارات الإعلانات.

5. تحديث بيانات الإعلان (مع إعادة ترتيب معقّدة)

PUT /admin/ads/{id}/update Bearer Token (Admin)

كل الحقول اختيارية هنا (sometimes) — أرسل فقط الحقول التي تغيّرت فعلاً. لكن حقل الترتيب يخضع لمنطق تلقائي مختلف تماماً حسب ما إذا غيّرت المكان أو فقط الترتيب داخل نفس المكان.

تم إرسال position و/أو sort_order جديد
←
الحالة أ: تغيّر المكان (position)
الحالة ب: نفس المكان، تغيّر الترتيب فقط
الحالةما يفعله الباك إند تلقائياً
تغيير المكان بالكامل 1) يُزاح كل ما بعد الإعلان في المكان القديم للأعلى (سد الفراغ).
2) في المكان الجديد: إذا الرقم المطلوب أكبر من (الأقصى + 1) يوضع تلقائياً في النهاية، وإلا يُزاح كل ما هو ≥ الرقم المطلوب للأسفل لإفساح مكان له.
نفس المكان، تغيّر الترتيب فقط إن كان الرقم المطلوب أكبر من الأقصى الحالي، يُخفَّض تلقائياً ليساوي الأقصى الحالي (وليس +1 كما في الإنشاء — هذا فرق مهم عن store). ثم يُزاح كل ما بينهما باتجاه معاكس (تقديم الإعلان يُنزل من بينهم، تأخيره يُصعد من بينهم).
فخ مهم جداً: سلوك تجاوز الحد الأقصى مختلف بين الإنشاء والتحديث عند الإنشاء (store)، رقم ترتيب أكبر من الحد الأقصى يُوضع في نهاية القائمة (max + 1). لكن عند التحديث (update) لنفس المكان، نفس الحالة تُخفَّض الرقم ليصبح مساوياً للحد الأقصى الحالي فقط (max، وليس max + 1). يعني لو أرسلتَ رقماً وهمياً كبيراً في التحديث ظناً أنه سيضع الإعلان في آخر القائمة، فقد لا يحصل ذلك بدقة كما توقعت. الحل الأنسب لواجهة Angular: لا تسمح للمستخدم بكتابة رقم ترتيب يدوياً من حقل نصي — اجعل إعادة الترتيب عبر سحب وإفلات (Drag & Drop) في الجدول، واحسب الرقم النهائي تلقائياً بناءً على الموضع الجديد الفعلي في القائمة المعروضة، ثم أرسله للـ API واعتمد فقط على القيمة المُعادة في الاستجابة لتحديث الواجهة.
مثال طلب (تغيير الترتيب فقط داخل نفس المكان)
{ "sort_order": 1 }
استجابة 200
{ "success": true, "message": "تم تحديث البيانات بنجاح", "data": { "id": "...", "sort_order": 1, "...": "..." } }
فخ: يجب إعادة تحميل القائمة كاملة بعد أي عملية ترتيب استجابة التحديث تُرجع فقط الإعلان الذي تم تعديله، بينما إعادة الترتيب تغيّر sort_order لإعلانات أخرى ضمنياً في قاعدة البيانات دون إرجاعها في الاستجابة. لذلك بعد أي عملية سحب/إفلات ناجحة، على Angular إعادة استدعاء GET /admin/ads لتحديث كامل الجدول بدل تعديل عنصر واحد محلياً فقط — وإلا ستظهر أرقام ترتيب غير متزامنة بين الشاشة وقاعدة البيانات.

6. حذف الإعلان

DELETE /admin/ads/{id}/delete Bearer Token (Admin)
استجابة 200
{ "success": true, "message": "تم حذف الإعلان بالكامل وإعادة ضبط الترتيب" }
عملية غير قابلة للتراجع الحذف يمسح صف الإعلان من قاعدة البيانات وصورته من التخزين السحابي معاً، بشكل نهائي بلا أرشفة (لا يوجد Soft Delete هنا كما في مسار حذف الزبائن مثلاً). يجب إظهار مودال تأكيد صريح قبل الاستدعاء دائماً ("سيتم حذف هذا الإعلان وصورته نهائياً، هل أنت متأكد؟").
إعادة الترتيب تلقائية بعد الحذف، يُعاد تلقائياً ترتيب بقية إعلانات نفس المكان (كل ما كان بعده يُنقَص ترتيبه بمقدار 1) — لا حاجة لأي منطق إضافي في الفرونت سوى إعادة استدعاء القائمة بعد نجاح الحذف.

7. تفعيل / إيقاف سريع للإعلان

POST /admin/ads/{id}/toggle-status Bearer Token (Admin)

مسار مخصص فقط لعكس قيمة is_active بضغطة واحدة (سويتش/Toggle في الجدول)، بدون الحاجة لإرسال كل بيانات الإعلان كما في مسار التحديث الكامل. لا يستقبل أي Body — الـ id في الرابط وحده كافٍ.

الطلب
POST /admin/ads/b1f5c2b0-.../toggle-status
(بدون Body)
استجابة 200 — نجاح
{
  "success": true,
  "message": "تم تغيير حالة الإعلان",
  "is_active": false
}
فخ: شكل استجابة مختلف عن باقي المسارات كل المسارات الأخرى (store, update, show...) تُرجع الإعلان كاملاً تحت مفتاح data. هذا المسار وحده لا يُرجع data إطلاقاً — فقط is_active كحقل مستقل في جذر الاستجابة (Top-level). لا تحاول قراءة response.data.is_active هنا، بل response.is_active مباشرة، وحدّث فقط قيمة السويتش محلياً في الجدول (Optimistic Update) دون الحاجة لإعادة تحميل الصف كاملاً.
الفرق عن استخدام PUT /update لنفس الغرض هذا المسار أخف وأسرع للسويتش السريع في الجدول لأنه لا يمر بأي منطق تحقق (Validation) أو إعادة ترتيب (سويتشات الحالة لا تُغيّر position ولا sort_order إطلاقاً). استخدم هذا المسار لسويتش الحالة السريع، واحفظ PUT /update لنموذج التعديل الكامل فقط.

فخ مشترك مع مسار الأدمن: نفس بنية الكائن المفتاحي هذا المسار يرجع نفس بنية data ككائن مفاتيحه position (وليس مصفوفة) تماماً كمسار الإدارة — نفس منطق التعامل مع الاستجابة مطلوب في Flutter (المرور على المفاتيح، وليس افتراض قائمة مباشرة).
فخ: لا يوجد Pagination هذا المسار يرجع كل الإعلانات الصالحة دفعة واحدة بدون أي تقسيم صفحات (limit/page). إذا زاد عدد الإعلانات النشطة مستقبلاً بشكل كبير، سيزداد حجم الاستجابة بدون حد أقصى. لا تفترض في Flutter وجود معاملات page أو per_page — هي غير مدعومة حالياً.
فخ: قوائم الأدمن والمشتري ليستا نفس الكاش رغم تطابق شكل البيانات، مسار الأدمن (/admin/ads) يعيد كل الإعلانات بينما مسار المشتري (/ads) يعيد جزءاً منها فقط بشرط فلترة مختلف تماماً (وأيضاً middleware مختلف كلياً: محمي مقابل عام). لا تشارك أي Cache أو نتيجة استدعاء واحدة بين لوحة الإدارة وتطبيق المشتري حتى لو كانا يعرضان "نفس البيانات" ظاهرياً.
استخدام target_type/target_url/target_id عند الضغط على الإعلان عند نقر المستخدم على بانر: إذا target_type = external افتح target_url في متصفح خارجي/WebView. إذا كانت product/shop/category استخدم target_id للانتقال داخلياً للشاشة المناسبة داخل التطبيق. تذكّر: الباك إند لا يضمن اتساق هذه الحقول (انظر التحذير في قسم الإنشاء)، لذا تعامل مع القيم الناقصة بأمان (مثال: لا تفتح رابطاً فارغاً).

نصائح عملية لتفادي الاحتكاك مع الباك إند

  1. لا تبني منطق ترتيب (sort_order) بنفسك في الفرونت — أرسل فقط الموضع المطلوب واعتمد دائماً على القيمة المُعادة من الـ API، وأعد تحميل القائمة كاملة بعد أي عملية سحب/إفلات.
  2. عامل حقل data في مسار جلب القوائم (index) دائماً ككائن مفتاحي (Object) مبني على position، وليس كمصفوفة — في كل من Angular وFlutter.
  3. افرض الترابط المنطقي بين target_type و target_id/target_url من طرف الفرونت بنفسك، فالباك إند لا يتحقق من ذلك.
  4. تعامل مع 404 و422 بشكل مختلف عن استجابات النجاح — أشكال JSON مختلفة تماماً وليست موحّدة عبر كل الحالات.
  5. استخدم image_url كما يُعاد من الـ API مباشرة كرابط صورة جاهز، بدون أي تركيب إضافي.
  6. أظهر تأكيداً صريحاً قبل الحذف وقبل استبدال صورة موجودة — كلاهما غير قابل للتراجع.
  7. استخدم POST /toggle-status للسويتش السريع فقط، وتذكّر أن استجابته لا تحتوي data — الحقل is_active في جذر الاستجابة مباشرة.
  8. لا تستدعِ أي مسار من مسارات /admin/* من تطبيق Flutter؛ هذه المسارات لواجهة Angular الإدارية فقط. المسار العام GET /ads هو الوحيد المشترك بين Angular وFlutter.
