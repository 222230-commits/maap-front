عرض قائمة منتجات التاجر وميزة البحث

شرح مركّز لمسار GET /store/products بعد إضافة حقل البحث، مبني على كود ProductService::listProducts الفعلي، مع كل الفخاخ الخفية التي يجب أن ينتبه لها الفرونت قبل الربط.

المسار والاستجابة

GET /store/products

Query Params المدعومة

الباراميترمطلوبالقيمة الافتراضيةالوصف
tabلاallيحدد أي مجموعة منتجات تُعرض في القائمة
searchلاnullبحث نصي في عنوان المنتج فقط
categoryلاnullمعرّف UUID للتصنيف، أو اسمه النصي
لا يوجد باراميتر per_page عدد العناصر بكل صفحة مثبّت داخلياً على 15 (paginate(15)). أي قيمة ترسلها الواجهة لتغيير حجم الصفحة سيتم تجاهلها تماماً لأن الكود لا يقرأها أصلاً.

مثال الطلب

GET /store/products?tab=all&search=قميص&category=3f1a9c2e-... Authorization: Bearer <token>

شكل الاستجابة الناجحة (200)

{ "success": true, "data": { "stats": { "all": 128, "published": 92, "out_of_stock": 6, "low_stock": 9, "draft": 14, "unpublished": 8, "blocked": 3, "trashed": 4 }, "products": { "current_page": 1, "data": [ // المنتجات الفعلية هنا ], "per_page": 15, "total": 92, "last_page": 7 } } }
تعشيش مزدوج لكلمة data لاحظ أن مصفوفة المنتجات الفعلية ليست في response.data مباشرة، بل في response.data.products.data، لأن Laravel Paginator يضيف طبقة data خاصة به فوق طبقة data التي يضيفها الـ Controller. الوصول الصحيح للمصفوفة هو response.data.products.data، وليس response.data.products ولا response.data.

حالة الخطأ (500)

{ "success": false, "message": "حدث خطأ أثناء جلب المنتجات.", "error": "Internal Server Error" }
تنويه حقل error يحمل تفاصيل تقنية فقط في بيئة التطوير (APP_DEBUG مفعّل). في بيئة الإنتاج ستكون قيمته دائماً "Internal Server Error"، لذا لا تعتمد الواجهة على محتواه لعرض رسالة مخصصة للمستخدم.

آلية البحث بالتفصيل

البحث يُطبَّق على حقل title فقط باستخدام ILIKE '%search%' (بحث جزئي غير حساس لحالة الأحرف). لا يشمل البحث الوصف، الكلمات المفتاحية، أو المميزات.

لا يوجد أي تحقق (Validation) على قيمة search القيمة تُمرر كما هي من الـ query مباشرة لطبقة الفلاتر بدون أي فحص طول أو تنقية للأحرف الخاصة. لا يوجد حد أقصى لطول نص البحث من جهة الباك إند حالياً، لذا يُفضّل أن تفرض الواجهة حداً معقولاً (مثلاً 100 حرف) لتفادي إرسال نصوص طويلة بلا داعٍ.
Debounce إلزامي لا ترسل طلب مع كل حرف يكتبه المستخدم. استخدم تأخير 300-400ms بعد آخر حرف قبل إرسال الطلب، وألغِ أي طلب سابق لم يكتمل بعد لتفادي وصول نتيجة بحث قديمة بعد نتيجة أحدث منها (race condition).

فخ إحصائيات التبويبات (الأهم)

كائن stats يُحسب من استعلام منفصل تماماً عن استعلام قائمة المنتجات، وهذا يخلق سلوكاً قد يُفهم خطأً:

استعلام الإحصائيات (statsQuery) يُطبَّق عليه فلترا search وcategory فقط
↓
استعلام قائمة المنتجات (query) يُطبَّق عليه tab بالإضافة إلى search وcategory
أرقام التبويبات لا تتغير حسب التبويب المختار مهما كان التبويب الحالي الذي يقف عليه المستخدم (all أو published أو أي تبويب آخر)، فإن الأرقام الظاهرة على كل التبويبات (128، 92، 14، ...) تبقى ثابتة — لأنها لا تُفلتَر بـ tab إطلاقاً. التبويب يغيّر فقط القائمة المعروضة أسفل الشريط. بالمقابل، الأرقام نفسها تتغير فوراً إذا كتب المستخدم نص بحث أو اختار تصنيفاً، لأن هذين الفلترين يُطبَّقان على استعلام الإحصائيات أيضاً. الخلاصة للواجهة: اربط تحديث الأرقام بتغيّر search أو category فقط، ولا تتوقع أو تحاول إعادة حسابها عند مجرد الضغط على تبويب مختلف — الباك إند لن يغيّرها في هذه الحالة.

فلتر التصنيف

يقبل باراميتر category شكلين مختلفين للقيمة:

شكل القيمةطريقة المطابقة
UUID أو رقممطابقة مباشرة على categories.id
أي نص آخرمطابقة تامة (=) على categories.name، وليست مطابقة جزئية
مطابقة الاسم حرفية وليست تقريبية لو أرسلت الواجهة اسم تصنيف كنص (بدل الـ id) فيجب أن يكون مطابقاً تماماً بما فيه حالة الأحرف والمسافات، وإلا فلن يُعيد الاستعلام أي نتائج. الأسلم للواجهة أن ترسل دائماً id التصنيف الذي حصلت عليه من مسار جلب تصنيفات المتجر (GET /store/categories) بدلاً من الاسم النصي.

الترقيم (Pagination)

النتائج مرتبة تنازلياً حسب created_at، وعدد كل صفحة ثابت على 15 عنصراً. للانتقال بين الصفحات أرسل باراميتر page الافتراضي في Laravel (مثال: ?page=2) — وهو يعمل تلقائياً لأن الكود يستخدم paginate() القياسية، رغم أنه غير مذكور صراحة في مصفوفة الفلاتر بالـ Controller.

تطبيق Angular (الشاشة + خدمة البحث)

الخدمة

import { Injectable } from '@angular/core'; import { HttpClient, HttpParams } from '@angular/common/http'; import { Observable } from 'rxjs'; export interface ProductListResponse { success: boolean; data: { stats: Record<string, number>; products: { data: any[]; current_page: number; last_page: number; total: number; }; }; } @Injectable({ providedIn: 'root' }) export class ProductsService { constructor(private http: HttpClient) {} listProducts(params: { tab?: string; search?: string; category?: string; page?: number }) : Observable<ProductListResponse> { let httpParams = new HttpParams(); if (params.tab) httpParams = httpParams.set('tab', params.tab); if (params.search) httpParams = httpParams.set('search', params.search); if (params.category) httpParams = httpParams.set('category', params.category); if (params.page) httpParams = httpParams.set('page', params.page); return this.http.get<ProductListResponse>('/store/products', { params: httpParams }); } }

الكومبوننت

import { Component, OnInit, OnDestroy } from '@angular/core'; import { FormControl } from '@angular/forms'; import { Subject } from 'rxjs'; import { debounceTime, distinctUntilChanged, takeUntil } from 'rxjs/operators'; import { ProductsService } from './products.service'; @Component({ selector: 'app-product-list', templateUrl: './product-list.component.html' }) export class ProductListComponent implements OnInit, OnDestroy { searchControl = new FormControl(''); currentTab = 'all'; stats: Record<string, number> = {}; products: any[] = []; private destroy$ = new Subject<void>(); constructor(private productsService: ProductsService) {} ngOnInit(): void { this.searchControl.valueChanges.pipe( debounceTime(400), distinctUntilChanged(), takeUntil(this.destroy$) ).subscribe(value => this.fetch({ search: value ?? '' })); this.fetch({}); } onTabChange(tab: string): void { this.currentTab = tab; // ملاحظة: تغيير التبويب لا يعيد حساب this.stats، فقط يعيد جلب المنتجات this.fetch({ tab }); } private fetch(overrides: Partial<{ search: string; tab: string; category: string }>): void { const params = { tab: overrides.tab ?? this.currentTab, search: overrides.search ?? this.searchControl.value ?? '', category: overrides.category }; this.productsService.listProducts(params).pipe( takeUntil(this.destroy$) ).subscribe(res => { this.stats = res.data.stats; this.products = res.data.products.data; // انتبه للتعشيش المزدوج }); } ngOnDestroy(): void { this.destroy$.next(); this.destroy$.complete(); } }
لماذا Angular هنا تحديداً الشاشة تجمع بين جدول بيانات، شريط تبويبات بحالات متعددة، وتحديد جماعي — هذا النمط (جداول + حالات فلترة متعددة) يناسب Angular/React أكثر من تجربة تصفح متسلسلة على الموبايل، خصوصاً أن لوحة التاجر أصلاً تُدار عبر واجهة ويب (/store/web/dashboard).

جدول ملخص الأخطاء المتوقعة

الكوديظهر فيالمعنىماذا يفعل الفرونت
200 كل الحالات الناجحة الطلب نجح، حتى لو كانت النتائج فارغة (مصفوفة products.data فارغة) اعرض حالة "لا توجد نتائج" إذا كانت المصفوفة فارغة، وليس رسالة خطأ
500 أي استثناء غير متوقع داخل index() خطأ عام في السيرفر (اتصال قاعدة بيانات، خطأ برمجي، الخ) اعرض رسالة عامة "تعذر تحميل المنتجات، حاول لاحقاً" وأتح زر إعادة المحاولة

نصائح عملية لتفادي الاحتكاك مع الباك إند

  1. لا تحسب أرقام التبويبات بنفسك في الفرونت — استخدم دائماً data.stats القادمة من السيرفر، ولا تتوقع تغيّرها عند تبديل التبويب فقط.
  2. اقرأ المنتجات من data.products.data وليس data.products مباشرة.
  3. أرسل category كـ id دائماً وليس كاسم نصي، لتفادي مشاكل المطابقة الحرفية.
  4. لا ترسل باراميتر لحجم الصفحة — استخدم page فقط للتنقل، والحجم ثابت على 15.
  5. طبّق debounce على حقل البحث (300-400ms) وألغِ الطلبات القديمة عند كتابة نص جديد.
  6. لا تعتمد على حقل error في رسائل الخطأ 500 لعرضه للمستخدم — استخدم message فقط.

ملاحظة مقترحة لفريق الباك إند

اقتراح تحسين لو أضاف الباك إند فلترة tab على استعلام الإحصائيات أيضاً (أو أعاد كائن إحصائيات منفصل لكل تبويب)، سيصبح ممكناً عرض عدّاد "النتائج ضمن هذا التبويب بعد البحث" دون حسابات إضافية في الفرونت. هذا اختياري وليس عائقاً حالياً، لكنه يوضّح تجربة الفرز للمستخدم أكثر.
