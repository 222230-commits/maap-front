تقييم المنتج بالنجوم (Rate)

هذا الدليل يغطي مسار تقييم المنتج بالنجوم فقط (POST rate) من ReviewController. لا يغطي مسار التعليق النصي (comment) بحسب الطلب.

1. نظرة عامة واختيار الأداة

الميزةالأداة المقترحةالسبب
شاشة تقييم المنتج بالنجوم Flutter (تطبيق الموبايل) تفاعل بسيط ومتسلسل (اختيار نجوم ثم إرسال) داخل رحلة تصفح المنتج على الموبايل، لا يحتاج جداول أو لوحة تحكم.
لماذا ليست Angular/React؟ هذه الميزة ليست لوحة تحكم فيها جداول أو تعديل جماعي، بل إجراء واحد بسيط ضمن رحلة المستخدم على تطبيق الموبايل، لذلك Flutter أنسب.

3. المسار: تقييم المنتج بالنجوم

POST /Buyer/review/products/{product}/rate

محمي بـ auth:sanctum — يتطلب Bearer Token. {product} يُربط تلقائياً عبر Route Model Binding.

مثال الطلب

{
  "rating": 4
}
الحقلالقاعدة
ratingrequired, integer, min:1, max:5

أشكال الاستجابة

200 - نجاح (إنشاء أو تحديث)

{
  "message": "تم حفظ التقييم بنجاح.",
  "data": {
    "id": 12,
    "buyer_id": 55,
    "product_id": 9,
    "order_item_id": 301,
    "rating": 4,
    "comment": null,
    "created_at": "...",
    "updated_at": "..."
  }
}

422 - فشل التحقق (Laravel القياسي)

{
  "message": "The rating field is required.",
  "errors": {
    "rating": ["The rating field is required."]
  }
}

403 - محاولة تقييم منتج تابع للمستخدم نفسه

{
  "error": "عملية غير مصرح بها: لا يمكنك تقييم منتج تابع لمتجرك."
}

403 - المستخدم لم يشترِ / يستلم المنتج

{
  "error": "عفواً، يجب عليك شراء وتجربة هذا المنتج أولاً لتتمكن من إعطاء رأيك فيه."
}
فخ: شكلا استجابة خطأ مختلفان تماماً أخطاء التحقق (422) تأتي بمفتاح errors (كائن فيه مصفوفات)، بينما أخطاء منطق العمل (403) تأتي بمفتاح مسطح error (نص واحد). لا تفترض شكلاً واحداً للأخطاء في الفرونت — تحقق أولاً من الحالة (status code) ثم اقرأ المفتاح المناسب.
فخ: نفس status code (403) لسببين مختلفين الحالتان (منتج المستخدم نفسه / لم يشترِ المنتج) ترجعان 403 بالضبط. لا يمكن التمييز بينهما من الكود وحده، بل يجب قراءة نص error نفسه لعرض الرسالة الصحيحة أو اتخاذ إجراء مختلف (مثال: إخفاء زر التقييم بالكامل في الحالة الأولى، توجيه المستخدم لصفحة الطلب في الحالة الثانية).
فخ: لا وسيلة لمعرفة "إنشاء" أم "تحديث" من الرد الباك إند يستخدم updateOrCreate فيحسب داخلياً إن كان السجل جديداً أم موجوداً، لكنه لا يُعيد أي حقل يوضح ذلك في الـ JSON. إن احتجت تمييز "أول تقييم" عن "تعديل تقييم"، قارن ببيانات سبق أن جلبتها (مثال: هل كان عندك تقييم محفوظ مسبقاً في الشاشة) بدلاً من الاعتماد على الاستجابة.

شروط الأحقية (checkEligibilityAndGetOrderItem)

الشرطالتفصيل
ليس صاحب المنتجيُقارن product.shop.seller_id بمعرف المستخدم الحالي
اشترى واستلم المنتج فعلياًيجب وجود order_item ضمن طلب حالته completed بالضبط لهذا المنتج تحديداً لهذا المشتري
ربط أحدث طلبعند وجود أكثر من طلب completed لنفس المنتج، يُربط التقييم دائماً بأحدث order_item_id (الأحدث حسب تاريخ الطلب)
فخ: حالات الطلب الأخرى لا تكفي وجود طلب بحالة "قيد الشحن" أو "تم التسليم لشركة الشحن" (أي شيء غير completed حرفياً) لا يمنح أحقية التقييم. يجب أن تُظهر شاشة الطلب في التطبيق أن التقييم متاح فقط بعد أن يصبح الطلب completed (بعد تأكيد الاستلام)، وليس فقط بعد الشراء.
فخ: إعادة التقييم قد تغيّر ربط الطلب دون إشعار إن اشترى المستخدم نفس المنتج مرة أخرى وأكمل طلباً جديداً، ثم عدّل تقييمه القديم، سيُعاد ربط التقييم بـ order_item_id الجديد تلقائياً دون أي إشارة في الاستجابة تفيد بأن الربط تغيّر.

عنصر النجوم تحديداً هو حقل rating في جسم الطلب. زر "حفظ التقييم" معطّل/مخفي ما لم تتأكد الشاشة مسبقاً (من بيانات الطلب) أن حالته completed — وإلا سيصطدم المستخدم بخطأ 403 غير متوقع بعد الضغط.

6. نصائح عملية لتفادي الاحتكاك مع الباك إند

  1. لا تعتمد على status code وحده للتفريق بين نوعي خطأ 403 — اعرض نص error كما هو من الخادم.
  2. فعّل زر/عنصر التقييم في واجهة المستخدم فقط بعد التأكد من أن حالة الطلب completed، لتقليل عدد أخطاء 403 غير الضرورية.
  3. عامل استجابة 200 دائماً كـ "أحدث نسخة من التقييم" — لا تحتفظ بنسخة محلية قديمة من order_item_id بعد أي عملية حفظ ناجحة.
  4. تعامل مع شكل الاستجابة 422 (بمفتاح errors) بشكل منفصل تماماً عن شكل 403 (بمفتاح error) في طبقة معالجة الأخطاء بالتطبيق.
  5. لا تستنتج من الاستجابة ما إذا كانت العملية "إنشاء" أم "تعديل" — إن احتجت هذا الفرق، اعتمد على ما إذا كانت الشاشة تعرض تقييماً محفوظاً مسبقاً قبل الإرسال.

7. ملاحظة مقترحة لفريق الباك إند

الحالتان الحاليتان لخطأ 403 في دالة checkEligibilityAndGetOrderItem تتشابهان تماماً في status code، مما يجبر الفرونت إند على المطابقة النصية لرسالة الخطأ لتمييز السببين. يُفضّل إضافة حقل error_code ثابت (مثال: OWN_PRODUCT_REVIEW_FORBIDDEN و PURCHASE_REQUIRED) بجانب رسالة error النصية، ليتعامل الفرونت مع الحالتين برمجياً دون الاعتماد على نص قابل للتغيير مستقبلاً.

دليل داخلي لفريق الفرونت إند — يغطي مسار rate فقط ضمن ReviewController.
