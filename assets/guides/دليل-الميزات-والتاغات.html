مشكلة shop_id = null — كيف يتفاداها الفرونت

الفخ لا تفحص الواجهة "هل shop_id فارغ؟" لتقرير إظهار أزرار التعديل/الحذف. المصدر الصحيح للحقيقة هو from — أي من أي مصفوفة أتى العنصر: system_features أو merchant_features (وبالمثل system_tags/merchant_tags). الباك إند نفسه يفصلهم بهذا الأساس في getSeparatedFeatures/getSeparatedTags، وأي عملية تعديل/حذف من طرف التاجر مقيّدة فعلياً بـ where('shop_id', $merchantShopId) — فلو مررت ID لعنصر نظامه shop_id = null، الباك إند يرجع خطأ منطقي (404/400) وليس خطأ null.
التوصية عند جلب البيانات، أضف حقلاً مشتقاً في نموذج الفرونت مثل isEditable = (source === 'merchant') بدل تمرير shop_id الخام إلى منطق العرض. هذا يمنع أي انزلاق مستقبلي لو الباك إند غيّر شكل الحقل.

تصفح الميزات/التاغات + البحث (Seller)

GET/store/features?search=شاشة وبالمثل /store/tags

يرجع دائماً كائنين منفصلين — لا قائمة واحدة مدموجة — والبحث اختياري عبر query param واحد فقط.

// نموذج الاستجابة — 200
{
  "success": true,
  "data": {
    "system_features":   [ { "id": "uuid", "name": "شاشة لمس", "shop_id": null } ],
    "merchant_features":[ { "id": "uuid", "name": "توصيل مجاني", "shop_id": "shop-uuid" } ]
  }
}
فرق جوهري عن Admin هذا المسار بدون pagination — يرجع array كامل. لا تفترض وجود current_page/last_page هنا كما في لوحة الأدمن، وإلا كودك الموحّد بين الشاشتين سينكسر.
فشل صامت في try/catch العام أي استثناء غير متوقع هنا يرجع رسالة عامة ثابتة "حدث خطأ أثناء جلب الميزات الفنية" بكود 500 — لن ترى تفاصيل الخطأ الحقيقي إطلاقاً من هذا الـ endpoint، فلا تعتمد على نص الرسالة لتشخيص مشاكل الشبكة/الفلترة أثناء التطوير.

GET/store/features/{featureId} 
// نجاح — 200

// فشل — 404 (غير موجود، أو خارج نطاقك)

رسالة إنجليزية وسط تطبيق عربي لاحظ أن getFeatureById/getTagById يرميان رسالة استثناء بالإنجليزية بينما باقي الرسائل في النظام كلها عربية. لا تعرض هذه الرسالة مباشرة للمستخدم النهائي — اعرض رسالة عربية ثابتة من الفرونت لهذه الحالة تحديداً ("العنصر غير موجود أو لا تملك صلاحية الوصول إليه").

إضافة سريعة (إنشاء أو ربط باسم نصي)

POST/store/features/create/{productId} body: { name } 
// نجاح — 200
{ "success": true, "message": "تم إضافة الميزة للمنتج بنجاح." }

// فشل — 400 (مثال: تجاوز 10 ميزات)
{ "success": false, "message": "لا يمكن إضافة أكثر من 10 ميزة للمنتج الواحد." }
سلوك ضمني: بحث ثم إنشاء (find-or-create) هذا المسار لا يتحقق من وجود الاسم مسبقاً على مستوى الفرونت — الباك إند يبحث عن اسم مطابق ضمن (نظام + متجرك)، فإن لم يجده ينشئ ميزة جديدة بـ shop_id الخاص بمتجرك تلقائياً. يعني: كتابة اسم موجود فعلاً بالنظام سيربطه مباشرة دون تكرار، بينما اسم جديد كلياً سينشئ سجلاً دائماً في جدول الميزات حتى لو حذفت الربط لاحقاً بمنتج آخر — السجل نفسه لا يُحذف تلقائياً إلا عبر destroy صراحة.
توصية عرض اجعل حقل الإدخال autocomplete يبحث في نفس الوقت ضمن system_features/merchant_features المحمّلة مسبقاً (من endpoint الفهرسة) بدل الاعتماد فقط على منطق find-or-create في الباك إند — لتفادي إنشاء أسماء مكررة بصياغة مختلفة (مثال: "شاشة لمس" و"شاشة اللمس").

ربط متعدد بمعرّفات جاهزة (attach)

POST/store/features/{productId}/attach-feature body: { feature_ids: [uuid,...] } 
// نجاح — 200
{ "success": true, "message": "تم ربط الميزات بالمنتج بنجاح." }

// فشل تحقق الحقول — 422 (Laravel validation)
{ "message": "...", "errors": { "feature_ids": ["لا يمكنك ربط أكثر من 10 ميزات في المرة الواحدة."] } }

// فشل منطق عمل — 400
{ "success": false, "message": "واحدة أو أكثر من الميزات المحددة مرتبطة مسبقاً بهذا المنتج." }
القاعدةالتفاصيل
الحد الأقصى للطلب الواحد10 عناصر
التكرار داخل المصفوفةمرفوض (distinct)
التكرار مع الروابط الحاليةالعملية بأكملها تُرفض لو أي عنصر واحد مرتبط مسبقاً — وليس تجاهله فقط
الحد الإجمالي على المنتج10 كحد أقصى (الحالي + الجديد)
فخ: العملية Atomic بالكامل — كل أو لا شيء attachMultipleFeatures تُنفَّذ داخل DB::transaction. لو من ضمن 5 ميزات مرسلة، ميزة واحدة مرتبطة مسبقاً بالمنتج، الطلب كله يفشل ولا يُربط ولا ميزة واحدة — حتى الأربعة الصالحة. لا تصمّم الواجهة على افتراض "سيتم ربط اللي ينجح وتجاهل الباقي". اعرض رسالة الخطأ وحدد بوضوح للمستخدم أن عليه إزالة العناصر المكررة من التحديد قبل إعادة المحاولة.

فك ربط متعدد (detach)

DELETE/store/features/{productId}/detach-feature body: { feature_ids: [uuid,...] }
عملية لا رجعة فيها + Atomic أيضاً فك الربط نهائي (لا Soft Delete). ونفس منطق "الكل أو لا شيء": لو عنصر واحد من المصفوفة غير مرتبط أصلاً بالمنتج، الطلب كامل يُرفض بـ400 قبل حذف أي شيء. اعرض تأكيداً صريحاً (confirm dialog) قبل الإرسال دائماً.

تعديل عنصر يملكه التاجر

PUT/store/features/update/{id} body: { name }
تطبيع صامت على اسم الميزة (وليس التاغ) فقط في updateMerchantFeature: الاسم يُمرّر عبر strip_tags ثم كل التكرارات المتتالية من المسافات تُستبدل بشرطة واحدة - عبر preg_replace. يعني لو المستخدم كتب "شاشة لمس عالية الدقة"، القيمة المخزَّنة فعلياً هي شاشة-لمس-عالية-الدقة. هذا التطبيع غير موجود إطلاقاً في updateMerchantTag (تعديل التاغ يُبقي المسافات كما هي). اعرض في الفرونت معاينة فورية للاسم بعد هذا التحويل قبل الحفظ حتى لا يفاجأ التاجر بالنتيجة.
تأثير جانبي مقصود الرسالة توضحه صراحة: "تم تحديث اسم الميزة بنجاح وتعديلها في كافة المنتجات المرتبطة" — لأن التعديل هنا على سجل الميزة نفسه في جدول features وليس نسخة لكل منتج. حدّث أي كاش محلي لكل المنتجات المرتبطة بهذه الميزة، لا شاشة المنتج الحالية فقط.

حذف عنصر يملكه التاجر

DELETE/store/features/delete/{id}
حذف نهائي متسلسل على كل المنتجات deleteMerchantFeature تحذف أولاً كل الروابط في product_features ثم تحذف الميزة نفسها — داخل معاملة واحدة. لا يوجد استرجاع. اعرض تحذيراً يذكر عدد المنتجات المتأثرة إن كان بالإمكان جلبه مسبقاً، لا مجرد "هل أنت متأكد؟" عامة.

مزامنة شاملة على المنتج (تنبيه نطاق)

PUT/store/products/{id}/features Validation عبر SyncProductFeaturesRequest
الكنترولر الفعلي لهذا المسار (SellerProductController::syncFeatures) غير متاح في الملفات المرفقة ما هو مؤكد من SyncProductFeaturesRequest: الطلب يقبل existing_features[] (UUIDs يجب أن تكون موجودة فعلاً في app.features) وnew_features[] (نصوص جديدة، حتى 10 لكل مصفوفة، والمجموع الكلي ≤ 10 عبر تحقق إضافي في withValidator). لكن شكل الاستجابة الدقيق ومنطق "هل يستبدل كل الميزات أم يضيف فقط" غير موثّق هنا لعدم توفر كود الكنترولر/الخدمة الفعلي. لا تفترض أنه يطابق سلوك updateProductFeatures في FeatureService (الذي يستبدل فقط ميزات التاجر نفسه ويُبقي ميزات النظام كما هي على المنتج) — أكّد هذا مع فريق الباك إند قبل بناء منطق "استبدال شامل" في الواجهة.
فخ إضافي داخل SyncProductTagsRequest نفسه ملف تحقق التاغات فيه مفاتيح رسائل خطأ ميتة (tags.array, tags.*.required...) لا تطابق أسماء الحقول الفعلية (existing_tags/new_tags) — أي أن Laravel لن يستخدمها أبداً وسيعرض رسائله الافتراضية الإنجليزية بدلاً منها عند فشل هذه القواعد تحديداً. كذلك existing_tags.* لا تحمل قاعدة required (بعكس existing_features) فقيمة null داخل المصفوفة قد تمر من قاعدة uuid. تحقق من الحقول على مستوى الفرونت بنفسك ولا تعتمد فقط على رسائل 422 القادمة من هذا الـ Request تحديداً.

إضافة عنصر نظام جديد

POST/admin/features/store body: { name } 
// نجاح — 200
{ "success": true, "message": "تم إضافة الميزة للنظام بنجاح." }
// فشل تكرار — 400
{ "success": false, "message": "الميزة موجودة مسبقاً." }
فحص التكرار محصور في نطاق النظام فقط الفحص هو where('name', $name)->whereNull('shop_id') — يعني إمكانية وجود اسم مطابق حرفياً بين ميزة نظام وميزة تاجر في نفس الوقت دون أي تعارض. هذا سلوك مقصود من الباك إند وليس خللاً، لكن يستحق تنبيه المستخدم في الواجهة عند البحث لتجنب الخلط البصري بين الاثنين إن ظهرا بنفس الاسم.

تعديل عنصر نظام

PUT/admin/features/{id}/update 
// نجاح — 200
{ "success": true, "message": "تم التحديث بنجاح." }
// فشل — 404
{ "success": false, "message": "الميزة غير موجودة." }
محاولة تعديل ميزة تاجر من هذا المسار تُرجع 404 وليس 403 لأن الشرط whereNull('shop_id') يمنع مطابقة أي صف مملوك لتاجر، فتُقرأ النتيجة كـ"صفر صفوف محدّثة" وتُترجم لرسالة "غير موجودة" — رغم أن الميزة موجودة فعلياً في قاعدة البيانات. لا تعرض هذه الرسالة حرفياً لو كنت متأكداً من السياق أن العنصر ملك تاجر؛ اعرض بدلاً منها "هذا العنصر يخص أحد التجار، استخدم force-delete/الحذف الخاص به" إن كان بالإمكان تمييز الحالتين مسبقاً من عمود "النوع" في الجدول.

حذف عادي (نظام فقط)

DELETE/admin/features/{id}/delete
فخ حرج: يرجع 200 نجاح دائماً حتى لو لم يُحذف شيء destroy العادي لا يتحقق من نتيجة الحذف إطلاقاً — يستدعي DB::transaction ثم يرجع {"success": true, "message": "تم الحذف بنجاح."} بشكل غير مشروط، حتى لو مررت ID لميزة تاجر (فلن تُحذف فعلياً بسبب whereNull('shop_id')) أو ID غير موجود أصلاً. لا تثق باستجابة 200 هنا كدليل على أن العنصر اختفى فعلاً — إن أردت تأكيد الحذف، أعد جلب القائمة أو تحقق أن العنصر من نوع "نظام" قبل استدعاء هذا المسار أصلاً.

حذف بالقوة (أي نوع — نظام أو تاجر)

DELETE/admin/features/{id}/force-delete 
// نجاح — 200
{ "success": true, "message": "تم حذف الميزة وفك ارتباطها من كافة المنتجات بنجاح." }
// فشل — 404
{ "success": false, "message": "الميزة غير موجودة." }
لا سقف نوع — أخطر مسار في هذا الدليل هذا المسار الوحيد القادر فعلياً على حذف ميزة/تاغ تاجر من لوحة الأدمن، ويحذف كل روابطها بجميع منتجات كل التجار دفعة واحدة، بلا استرجاع. اربطه بمودال تأكيد صريح يذكر اسم العنصر ونوعه (نظام/تاجر) بوضوح، ولا تضعه كإجراء افتراضي بجانب زر "حذف" العادي دون تمييز بصري قوي (لون أحمر أغمق + أيقونة تحذير).

ربط مباشر بمنتج من لوحة الأدمن

POST/admin/features/attach-to-product body: { product_id, feature_id }
عنصر واحد فقط لكل طلب، وبدون سقف 10 بعكس مسارات attachFeatures/attachTags للتاجر (max 10 عبر مصفوفة)، هذا المسار الإداري يقبل معرّفاً واحداً فقط في كل استدعاء ولا يتحقق من عدد الميزات الحالية على المنتج إطلاقاً — يمكن نظرياً تجاوز حد الـ10 الذي يفرضه الباك إند على التاجر لو استُخدم هذا المسار بشكل متكرر. صمّم الواجهة الإدارية كحلقة واحدة تلو الأخرى (loop) إن احتجت ربط عدة عناصر، وليس كطلب واحد بمصفوفة.

نصائح عملية لتفادي الاحتكاك مع الباك إند

  1. لا تبني منطق "نجاح جزئي" لعمليات attach/detach المتعددة — كل عملية Atomic بالكامل (كل أو لا شيء) لأنها داخل DB::transaction.
  2. اعتمد على مصدر القائمة (system_* مقابل merchant_*) لتقرير قابلية التعديل، لا على فحص shop_id === null مباشرة.
  3. لا تشارك نفس دالة parsing الاستجابة بين شاشة Seller (بدون pagination) وشاشة Admin (data.data مع pagination).
  4. عطّل عناصر مختارة مسبقاً في واجهة الاختيار المتعدد بدل الاعتماد فقط على رسالة الخطأ اللاحقة.
  5. ميّز بصرياً بين "حذف عادي" (نظام فقط، صامت الفشل) و"حذف بالقوة" (أي نوع، لا رجعة) في لوحة الأدمن — لا تضعهما بنفس شكل الزر.
  6. لتعديل اسم ميزة (وليس تاغ)، اعرض معاينة فورية للتحويل التلقائي للمسافات إلى شرطات قبل الحفظ.
  7. لمسار المزامنة الشاملة (/products/{id}/features و/tags)، أكّد مع الباك إند شكل الاستجابة الفعلي قبل البناء عليه — الكود المتاح يغطي التحقق فقط وليس التنفيذ.

ملاحظة مقترحة لفريق الباك إند

توحيد سلوك destroy عبر AdminFeatureController وAdminTagController الدالتان الحاليتان لا تتحقق من affected rows قبل إرجاع success: true. اقتراح: التحقق من قيمة ->delete() المرجعة (عدد الصفوف المتأثرة) وإرجاع 404 برسالة واضحة لو كانت صفراً — بنفس النمط المستخدم فعلياً في update() بنفس الملف. هذا سيمنع الفرونت من الاعتماد على استجابة 200 خادعة.
توحيد رسائل validation في SyncProductTagsRequest مفاتيح messages() الحالية (tags.array, tags.*.required...) لا تطابق أسماء الحقول الفعلية في rules() (existing_tags/new_tags) فلا تُستخدم أبداً. تحديثها لتطابق أسماء الحقول الحقيقية يوفر رسائل عربية متسقة مع باقي النظام بدل رسائل Laravel الإنجليزية الافتراضية.
دليل تكامل داخلي — يعكس حالة الكود وقت إعداد هذا الملف. أي تعديل لاحق في Controllers/Services يجب أن يُتبع بتحديث هذا الدليل.
