ميزة السلة (Cart)

هذا الدليل يشرح كل مسارات السلة (GET / POST / PUT / DELETE) بالتفصيل: شكل الطلب، كل احتمالات الاستجابة، وأهم الفخاخ التي قد تسبب مشاكل في الربط لو تم الاعتماد فقط على اسم الدالة.

2. مخطط تدفق: إضافة عنصر / التعديل مع الدمج

أهم نقطة هنا: عند تعديل عنصر (PUT) بحيث يصبح لونه/مقاسه مطابقاً لعنصر آخر موجود مسبقاً في نفس المنتج، يتم دمج العنصرين والاحتفاظ بمعرّف العنصر الآخر، ويُحذف العنصر الأصلي. أي أن cartItemId الذي تعمل عليه قد يختفي بعد نجاح الطلب!

3. مسارات API بالتفصيل

3.1 جلب السلة كاملة

GET/buyer/cart
الطلب: بدون body، فقط رأس التوثيق: 
Authorization: Bearer {token}
الاستجابة (200): 
{
  "cart_id": "uuid",
  "total_items_count": 5,
  "grand_total": 91.00,
  "shops": [
    {
      "shop_id": "uuid",
      "shop_name": "SHEGLAM",
      "shop_slug": "sheglam",
      "shop_logo_url": "https://...",
      "subtotal": 51.00,
      "items_count": 2,
      "items": [
        {
          "cart_item_id": "uuid",
          "product_id": "uuid",
          "title": "قلم تمويه الشفاه",
          "slug": "product-slug",
          "quantity": 1,
          "price": 200,
          "compare_at_price": 200,
          "discount_percentage": 0,
          "color_id": "uuid|null",
          "size_id": "uuid|null",
          "color_name": "Dream Date",
          "size_name": null,
          "total_price": 17.00,
          "stock": 200,
          "is_available": true,
          "image_url": "https://..."
        }
      ]
    }
  ]
}
الحقلالنوعملاحظة
pricenumberالسعر الحالي الفعلي (المستخدم فعلاً في حساب total_price)
compare_at_pricenumber أو nullالسعر "قبل الخصم" لعرضه مشطوباً — null إن لم يكن للمنتج سعر مقارنة أصلاً
discount_percentageintegerنسبة الخصم، محسوبة دائماً رياضياً من compare_at_price وprice — مضمونة كعدد صحيح
تحديث: تم توحيد مصدر الخصم discount_percentage أصبح الآن يُحسب دائماً رياضياً من الفرق بين compare_at_price وprice، ولم يعد يُقرأ من أي حقل مخزَّن منفصل بالمنتج. النتيجة: الحقلان أصبحا مترابطين بشكل مضمون — discount_percentage > 0 يعني بالضرورة أن compare_at_price ليست null وأكبر من price، والعكس صحيح. يمكنك الآن الاعتماد على أي منهما لتفعيل شارة الخصم أو السعر المشطوب دون قلق من تعارضهما.
تحديث: النوع أصبح int مضموناً الكود يستخدم الآن (int) round(...) صراحة، أي أن discount_percentage سيصلك دائماً كعدد صحيح (مثل 25 وليس 25.0) — يمكنك التعامل معه كـ int بثقة في لغات صارمة الأنواع.
فخ: تسمية متشابهة بمعنى مختلف items_count داخل كل متجر = عدد الأسطر (عدد أنواع المنتجات المختلفة)، بينما total_items_count على مستوى السلة الكلي = مجموع الكميات (quantity) لكل العناصر. لا يصح جمع قيم items_count من كل المتاجر وتوقع أن تساوي total_items_count — إحداهما تعدّ الأسطر والأخرى تعدّ القطع.
فخ: عناصر تختفي دون تنبيه إذا حُذف منتج من النظام (product = null)، يتم استبعاد عنصر السلة المرتبط به بالكامل من الاستجابة بصمت، دون أي رسالة أو حقل يوضح أن هناك عنصراً محذوفاً. إن كانت واجهتك تعرض عداد السلة من طلب سابق (مثلاً badge على أيقونة السلة) وقارنته بهذه الاستجابة، قد يظهر تناقض غير مفسَّر للمستخدم.
فخ: is_available لا يمنع شيئاً تلقائياً الحقل is_available محسوب فقط للعرض (نشط + منشور + المخزون كافٍ للكمية الحالية). الباك إند لا يحذف أو يعدّل العنصر تلقائياً إن أصبح غير متوفر — يبقى في السلة بكميته القديمة. الفرونت إند مسؤول عن تعطيل زر "اطلب" لأي متجر يحتوي عنصراً واحداً على الأقل بـ is_available: false.

3.2 إضافة عنصر للسلة

POST/buyer/cart/items
الطلب: 
{
  "product_id": "uuid",       // مطلوب
  "quantity": 1,               // اختياري، افتراضي 1، حد أدنى 1
  "color_id": "uuid",          // اختياري إلا إذا كان المنتج متعدد الألوان بلا صورة عامة
  "size_id": "uuid"            // اختياري
}
الاستجابة عند النجاح (201) — تم تحديثها الآن لترجع السلة كاملة: 
{
  "message": "تمت إضافة المنتج إلى السلة بنجاح.",
  "data": {
    "cart_id": "uuid",
    "total_items_count": 5,
    "grand_total": 91.00,
    "shops": [ ... نفس شكل GET بالكامل ... ]
  }
}
تحديث مهم منذ آخر نسخة شكل الاستجابة أصبح الآن مطابقاً تماماً لما يرجعه PUT: data هي السلة الكاملة عبر CartResource وليست سجل CartItem الخام كما كانت سابقاً. هذا يلغي الحاجة لاستدعاء GET إضافي بعد الإضافة — اعرض response.data مباشرة بعد نجاح الإضافة.
حالات الخطأ (400) — Business Exceptions:
الحالةمثال رسالة
المنتج غير موجود أو غير منشور"المنتج المطلوب غير موجود في النظام."
محاولة شراء من متجرك الخاصرسالة تتضمن اسم متجرك
اللون مطلوب ولم يُرسل"هذا المنتج متوفر بألوان محددة فقط..."
الكمية أكبر من المخزون المتاحرسالة نصية، مع حقل available_stock رقمي أحياناً (انظر التحذير التالي)
// شكل خطأ نفاد المخزون المتوقّع (قد لا يحتوي available_stock دائماً)
{
  "error": "الكمية المطلوبة أكبر من المخزون المتاح لمنتج ...",
  "available_stock": 3
}
فخ: حقل available_stock غير مضمون الظهور الكود الجديد يحاول إضافة available_stock فقط عندما يتحقق شرطان معاً: أن يكون الاستثناء من نوع BusinessException وأن يكون getCode() يساوي نص 'INSUFFICIENT_STOCK' بالضبط. دالة getCode() في استثناءات PHP القياسية ترجع رقماً افتراضياً وليس نصاً، فإن لم تكن BusinessException تخصّص هذا السلوك صراحةً، الشرط لن يتحقق أبداً وسيغيب الحقل بصمت دون أي خطأ ظاهر. لا تعتمد بشكل حصري على وجود available_stock — اجعل الفرونت يعرض دائماً نص error كخيار احتياطي، ويستخدم available_stock فقط إن وُجد فعلياً في الاستجابة.
فخ حرج: احتمال استجابة 500 بدل 400 الكود المرفق لا يستورد use App\Exceptions\BusinessException; في أعلى ملف CartController، بينما يستخدم instanceof BusinessException داخل catch. في PHP هذا يجعل الفحص يشير لكلاس غير موجود ضمن نيمسبيس الكنترولر نفسه، ما قد يسبب خطأ فادح (Fatal Error) بدل إرجاع استجابة 400 المتوقعة. الأثر على الفرونت: قد تصل أحياناً استجابة 500 بمحتوى غير متوقع (صفحة خطأ HTML أو JSON مختلف الشكل) بدل رسالة الخطأ العربية المنسّقة، حتى في حالات طبيعية تماماً مثل نفاد المخزون. تأكد أن معالج الأخطاء لديك يتحمّل حالة 500 بشكل لائق (رسالة عامة "حدث خطأ غير متوقع") بدل الافتراض أن كل خطأ سيصل بصيغة {"error": "..."}. تم إبلاغ فريق الباك إند بهذه النقطة (انظر القسم الأخير).
فخ: كودان مختلفان للخطأ أخطاء التحقق من الحقول (uuid غير صالح، الحقل فارغ) تُرجَع بكود 422 وبصيغة Laravel القياسية {"errors": {"field": ["..."]}}، بينما أخطاء منطق العمل (نفاد المخزون، منتج غير متاح...) من المفترض أن تُرجَع بكود 400 وبصيغة {"error": "...", "available_stock"?: number}. صمّم معالج أخطاء موحد في الفرونت يفرّق بين الشكلين، مع مسار احتياطي ثالث لأي كود آخر (500 وغيره).

3.3 تعديل عنصر (كمية/لون/مقاس)

PUT/buyer/cart/items/{cartItemId}
الطلب: 
{
  "quantity": 2,        // مطلوب، حد أدنى 1
  "color_id": "uuid",   // اختياري
  "size_id": "uuid"     // اختياري
}
الاستجابة عند النجاح (200): 
{
  "message": "تم تحديث السلة بنجاح.",
  "data": {
    "cart_id": "...",
    "total_items_count": ...,
    "grand_total": ...,
    "shops": [ ... نفس شكل GET بالكامل ... ]
  }
}
توصية تصميم نفّذ الشاشة بحيث تعيد رسم كامل السلة من response.data مباشرة بعد كل تعديل، بدل تحديث العنصر محلياً فقط بالـ id القديم — لأن العنصر قد يكون اندمج مع آخر واختفى id كما ذكرنا في المخطط أعلاه.
أخطاء (400): نفس أنواع أخطاء الإضافة (insufficientStock، invalidQuantity) بالإضافة إلى unauthorizedAction إذا لم يكن العنصر ملكاً للمستخدم أو غير موجود أصلاً — نفس رسالة الخطأ في الحالتين، فلا يمكن تمييز "العنصر غير موجود" عن "العنصر ليس لك" من نص الرسالة وحده.
نفس فخاخ POST تنطبق هنا حقل available_stock عند خطأ نفاد المخزون شرطي وغير مضمون لنفس السبب (استيراد BusinessException المفقود)، وهناك احتمال استجابة 500 غير متوقعة بدل 400 في أي حالة يُرمى فيها استثناء. استخدم نفس معالج الأخطاء الموحّد المذكور في قسم POST.

3.4 حذف عنصر واحد

DELETE/buyer/cart/items/{cartItemId}
الاستجابة (200) — تم تحديثها الآن لترجع السلة كاملة: 
{
  "message": "تم إزالة المنتج من السلة.",
  "data": {
    "cart_id": "uuid",
    "total_items_count": 3,
    "grand_total": 68.00,
    "shops": [ ... نفس شكل GET، محدَّث بعد الحذف ... ]
  }
}
تحديث مهم منذ آخر نسخة مسارات الإضافة (POST) والتعديل (PUT) والحذف (DELETE) أصبحت الثلاثة الآن متسقة تماماً: كل واحد منها يرجع data بنفس شكل CartResource الكامل. اعتمد نمطاً واحداً في الفرونت: بعد أي نجاح من الثلاثة، استبدل حالة السلة المحلية بالكامل بـ response.data دون تمييز خاص لكل مسار.
ملاحظة: كود الخطأ هنا لا يزال بلا حقل data عند فشل الحذف (400 - unauthorizedAction)، الاستجابة لا تزال {"error": "..."} فقط بدون بيانات سلة — هذا طبيعي ومتوقع لأن العملية لم تُنفَّذ أصلاً، فلا داعي لتحديث الحالة المحلية في حالة الفشل.

3.5 تفريغ السلة بالكامل

DELETE/buyer/cart/clear
الاستجابة (200) دائماً: 
{ "message": "تم تفريغ السلة بنجاح." }
فخ: عملية غير قابلة للتراجع، ولا تنتظر خطأ أبداً هذا المسار لا يرمي أي استثناء حتى لو كانت السلة فارغة أصلاً، ودائماً يرجع 200. لكنه يحذف كل عناصر السلة نهائياً من قاعدة البيانات دون تأكيد إضافي من الباك إند — التأكيد يجب أن يكون بالكامل من مسؤولية الفرونت (نافذة تأكيد قبل الاستدعاء).

4. شاشة السلة — التقسيم حسب المتجر

بما أن استجابة GET/PUT ترجع السلة مقسّمة مسبقاً داخل مصفوفة shops، لا حاجة للفرونت لتجميع العناصر يدوياً — فقط اعرض كل عنصر في المصفوفة كبطاقة متجر منفصلة، مع مجموع كل متجر وزر طلب خاص به.

فخ: لا يوجد مسار جاهز لطلب متجر واحد فقط الأكواد المرفقة لا تحتوي على أي endpoint لإنشاء طلب مرتبط بمتجر واحد تحديداً من السلة — فقط تعريف مسار عام POST /buyer/orders غير مرفق كوده. زر "اطلب من هذا المتجر" في الشاشة أعلاه يفترض أن هذا المسار يقبل shop_id لتصفية عناصر السلة عند إنشاء الطلب. يجب تأكيد هذا مع فريق الباك إند قبل البناء عليه فعلياً (انظر الملاحظة أدناه).
توصية تصميم عطّل زر الطلب لأي بطاقة متجر تحتوي عنصراً واحداً على الأقل بـ is_available: false، واعرض نص توضيحي تحت الزر بدل تركه مفعّلاً ويفشل الطلب لاحقاً في السيرفر.

6. نصائح عملية لتفادي الاحتكاك مع الباك إند

  1. وحّد استخدام مسار واحد فقط من بين /Buyer/Cart و /buyer/cart (المسجّلان مكرَّرين بنفس الوظيفة) — يُفضّل الأحرف الصغيرة لتفادي مشاكل الكاش أو الحساسية لحالة الأحرف على بعض الخوادم.
  2. لا تخزّن نسخة محلية من السلة أطول من مدة الجلسة الحالية دون مزامنة — الاختفاء الصامت للعناصر المحذوفة من الكتالوج يجعل أي كاش قديم مضللاً.
  3. بعد نجاح POST أو PUT أو DELETE على عناصر السلة، اعتمد نمطاً موحداً: استبدل حالة السلة بالكامل بـ response.data مباشرة — الثلاثة يرجعون الآن نفس شكل CartResource.
  4. اجعل معالج الأخطاء لديك يتحقق أولاً من الكود (422 / 400 / أي كود آخر مثل 500) قبل قراءة شكل الحمولة، لأن المفتاح يختلف (errors مقابل error)، وقد لا تصل أي حمولة JSON متوقعة في حالة 500.
  5. عامل حقل available_stock في أخطاء نفاد المخزون كحقل اختياري دائماً (error.available_stock ?? null) وليس حقلاً مضموناً.
  6. اعرض شارة الخصم والسعر المشطوب معاً بثقة الآن — discount_percentage وcompare_at_price مترابطان رياضياً ومضمونان بعد توحيد مصدر الحساب.
  7. عند حساب مجموع "اطلب من هذا المتجر"، استخدم subtotal الجاهز من الاستجابة بدل إعادة حسابه من العناصر لتفادي فروقات تقريب.
  8. تحقق من عمود is_available على مستوى كل عنصر داخل المتجر، وليس فقط على مستوى وجود stock رقمي، لأن التوفر يعتمد أيضاً على حالة نشر المنتج.

7. ملاحظة مقترحة لفريق الباك إند

مشكلة حرجة يُنصح بإصلاحها قبل النشر
  • CartController.php يستخدم instanceof BusinessException و$e->getCode() === 'INSUFFICIENT_STOCK' داخل catch في store() وupdate()، لكن لا يوجد use App\Exceptions\BusinessException; في أعلى الملف. هذا يجعل الفحص يشير لكلاس غير معروف ضمن نيمسبيس App\Http\Controllers\Buyer، وقد يسبب خطأ فادح (Fatal Error → استجابة 500) بدل استجابة 400 المقصودة، في أي حالة عادية مثل نفاد المخزون أو محاولة شراء من متجر خاص. يُنصح بإضافة الاستيراد المفقود واختبار كل حالات BusinessException فعلياً قبل الإطلاق.
  • يفترض الكود أن BusinessException::getCode() يرجع نصاً مثل 'INSUFFICIENT_STOCK'، بينما التوقيع القياسي لـException::getCode() في PHP يرجع عدداً صحيحاً. إن لم تكن BusinessException تُخصّص هذا صراحة، فحقل available_stock لن يظهر أبداً في الاستجابة رغم وجود الكود المخصص له.
نقاط تحسين تم تنفيذها بالفعل منذ آخر مراجعة
  • مسار POST لإضافة عنصر أصبح الآن يرجع CartResource كاملة بدل سجل CartItem الخام — جيد، ويطابق الآن سلوك PUT.
  • مسار DELETE لحذف عنصر أصبح يرجع الآن الإجماليات المحدثة أيضاً — الاتساق بين المسارات الثلاثة (POST/PUT/DELETE) أصبح تاماً.
  • أُضيف حقل available_stock اختيارياً في خطأ نفاد المخزون — بمجرد إصلاح مشكلة الاستيراد أعلاه سيعمل هذا الحقل كما هو مخطط له.
  • حقل discount_percentage أصبح يُحسب الآن من مصدر واحد فقط (رياضياً من compare_at_price وprice) بدل مصدرين متعارضين محتملين — تم حل مشكلة التناقض المذكورة سابقاً.
نقاط لا تزال قائمة
  • وجود نسخة مكررة تماماً من مجموعة مسارات /Cart و /cart يستحق التوحيد لتفادي التباس مستقبلي.
  • ملف الراوتس يستخدم BuyerOrderController::class ضمن مسارات buyer/orders دون استيراد الكلاس (لا يوجد use مقابل له في أعلى الملف)، بنفس نمط مشكلة BusinessException — يستحق المراجعة أيضاً لأنه سيمنع عمل مسارات الطلبات بالكامل عند استدعائها.
  • لا يوجد حالياً مسار مؤكد لإنشاء طلب مقتصر على متجر واحد من السلة — إن كانت ميزة "اطلب من هذا المتجر" مطلوبة فعلاً في الواجهة، يلزم تأكيد أو إضافة دعم shop_id في POST /buyer/orders.
دليل ربط داخلي — تم إنشاؤه من تحليل أكواد CartController / CartService / CartResource ومسارات routes/api.php الخاصة بالسلة.
