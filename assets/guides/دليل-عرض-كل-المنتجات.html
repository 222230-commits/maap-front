عرض جميع منتجات المنصة (Public Products)

دليل شامل لمسار GET /productsAll — يجلب كل منتجات المنصة عبر كل المتاجر دون شرط انتماء لمتجر معين، بنفس شكل استجابة منتجات المتجر الواحد. موجّه لفرق Flutter وAngular.

نظرة عامة واختيار الأداة

الميزةالأداة المقترحةالسبب
شاشة تصفح كل المنتجات (Infinite scroll) Flutter تجربة موبايل تصفح متسلسل بطاقات، وتحميل تدريجي عبر per_page وcurrent_page يناسب PageView/ListView.builder.
لوحة إدارة/مراجعة المنتجات مع فلترة متعددة الأقسام Angular جدول بيانات + شجرة اختيار أقسام متعددة (multi-select tree) لتوليد category_id مفصول بفواصل — أنسب لواجهة سطح مكتب فيها تحكم دقيق بالفلاتر.

تفاصيل المسار

GET /productsAll

لا يتطلب توكن. إن كان المستخدم مسجّل دخول عبر Sanctum يُمرَّر userId داخلياً إلى الخدمة (تأثيره الفعلي على الاستجابة غير موضّح في الكود المرفق — لا تفترضه في الفرونت دون تأكيد من الباك إند).

معاملات الطلب (Query Parameters)

الاسمالنوعإلزامي؟ملاحظات
per_pageintلا (افتراضي 20)حجم الصفحة
category_id / category_ids string | array لا ID واحد، أو مصفوفة، أو نص مفصول بفواصل "1,2,3"
فخ — أولوية المعامل إن أرسلت category_id وcategory_ids معاً، الكود يعتمد category_id فقط (??) ويتجاهل category_ids نهائياً. لا تصمم فرونت يرسل الاثنين متوقعاً دمجهما.
مثال Request
GET /productsAll?per_page=15&category_id=3,7,12
Response — نجاح (200)
{
  "success": true,
  "pagination": {
    "total": 128,
    "count": 15,
    "per_page": 15,
    "current_page": 1,
    "total_pages": 9
  },
  "data": [
    { "id": 1, "name": "...", "...": "حقول ProductDetailResource" }
  ]
}
Response — خطأ (500)
{
  "success": false,
  "message": "حدث خطأ أثناء تحميل المنتجات."
}
فخ — لا يوجد حقل error هنا بخلاف دالة index في نفس الكونترولر التي تُعيد error: $e->getMessage()، هذه الدالة لا تُعيد سوى message عند الفشل. أي معالج أخطاء عام (generic error handler) في الفرونت يفترض وجود error دائماً سيفشل بصمت هنا.
فخ — لا يوجد 404 لا شرط وجود متجر هنا (بخلاف showShopProductsById)، فمصفوفة data فارغة تعني ببساطة "لا نتائج مطابقة" وليست خطأ — لا تعامل الاستجابة الفارغة كحالة فشل.
توصية تصميم اعتمد على pagination.total_pages مقابل current_page لإخفاء مؤشر "تحميل المزيد" تلقائياً بدل الاعتماد على طول data فقط.

تحميل المزيد عند التمرير
GET /productsAll?per_page=…&category_id=…

الشرائح العلوية (chips) تُبنى من قائمة أقسام يجلبها الفرونت من مسار أقسام منفصل (غير موجود في هذا الكود)، والاختيار يُرسل كـ category_id نصياً مفصولاً بفواصل. "تحميل المزيد" يستدعي نفس المسار بـ current_page + 1 ويدمج النتائج بدل استبدالها.

جدول ملخص الأخطاء المتوقعة

الكوديظهر فيالمعنىماذا يفعل الفرونت
200 نجاح، حتى مع data: [] الطلب تم بنجاح — قد لا توجد نتائج مطابقة للفلترة اعرض حالة "لا توجد منتجات" وليس رسالة خطأ
500 أي استثناء غير متوقع في الخادم خطأ عام في الخادم أثناء التحميل اعرض message فقط (لا يوجد error) واسمح بإعادة المحاولة

نصائح عملية لتفادي الاحتكاك مع الباك إند

  1. لا تعتمد على وجود حقل error في أي استجابة فشل من هذا المسار تحديداً — تحقق من توفره لكل Endpoint على حدة قبل بناء معالج أخطاء عام موحّد.
  2. أرسل category_id فقط (وليس category_ids) لضمان تطبيق الفلترة، بصرف النظر عن اسم المتغير الذي تستخدمه داخلياً في الفرونت.
  3. عامل data: [] كحالة "فارغة" وليست خطأ — لا يوجد 404 لهذا المسار.
  4. اعتمد ترقيم الصفحات من كائن pagination المُعاد وليس من طول مصفوفة data فقط، لتفادي حسابات خاطئة عند آخر صفحة.

ملاحظة مقترحة لفريق الباك إند

توحيد شكل رسائل الخطأ دالة index() في نفس الكونترولر تُعيد error: $e->getMessage() عند الفشل، بينما showAllPublicProducts() لا تُعيده. يُفضّل توحيد شكل استجابة الخطأ بين كل دوال الكونترولر لتقليل الحالات الخاصة التي يجب على الفرونت التعامل معها يدوياً.
