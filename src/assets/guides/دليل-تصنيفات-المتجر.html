دليل تصفح وتعديل تصنيفات المتجر

مرجع مشترك للفرونت إند (Flutter / Angular) يغطي مسار تصفح المشتري الديناميكي، ومسار إدارة تصنيفات التاجر بخطواته الثلاث، مع كل الفخاخ التي يجب معرفتها قبل البرمجة.

1. أي أداة تُستخدم لكل جزء؟

القرار يعتمد على مكان ظهور الميزة، وليس على "الأفضل" بإطلاق.

الميزةالمكان الطبيعيالأداة المُوصى بهاالسبب
تصفح المشتري /dynamic تطبيق الجوال للمشتري Flutter تجربة Drill-down تُبنى بسهولة بـ Navigator.push وشاشة قائمة معاد استخدامها
إدارة تصنيفات المتجر (3 مسارات) لوحة تحكم التاجر (ويب) Angular تحتاج شجرة اختيار متعدد ومودالات تأكيد — نمط لوحة إدارة تتفوق فيه مكتبات الويب
ملاحظة كلا الميزتين تتقاسمان نفس مفهوم "الفرع الأخير" (is_leaf)، لذا يُفضّل عزل منطق شجرة التصنيفات في طبقة واحدة (Service / Repository) حتى لو استُخدمت الأداتان معاً.

2. تصفح المشتري الديناميكي

GET /Buyer/Categories/dynamic

يتيح للمشتري التنقل خطوة بخطوة داخل شجرة التصنيفات حتى يصل لفرع نهائي يمكن تصفح منتجاته.

الطلب

{ "parent_id": "uuid | null" }

عدم إرسال parent_id = طلب الجذور. إرساله = طلب أبناء ذلك القسم.

الاستجابة — تصفح عادي

{
  "success": true,
  "is_leaf": false,
  "current_parent": { "id": "...", "name": "ملابس رجالية", "parent_id": "..." },
  "data": [
    { "id": "...", "name": "قمصان",   "is_leaf": false, ... },
    { "id": "...", "name": "فساتين",  "is_leaf": true,  ... }
  ]
}

الاستجابة — وصل لفرع نهائي

{
  "success": true,
  "is_leaf": true,
  "current_parent": { "id": "...", "name": "فساتين سهرة" },
  "message": "هذا القسم هو نهاية الشجرة...",
  "data": []
}
⚠️ الفخ الأهم في هذا المسار لا تخلط بين is_leaf على المستوى الأعلى (يخص القسم الأب الذي تتصفحه) وبين is_leaf داخل كل عنصر من data (يخص ذلك العنصر تحديداً). استخدم الثاني لتقرر فوراً: افتح شاشة منتجات مباشرة، أو نادِ /dynamic مرة أخرى — لا داعي لانتظار استجابة "فرع نهائي" لتعرف ذلك مسبقاً.

4. الخطوة 1 — الحفظ بالمزامنة

POST /categories
{ "category_ids": ["uuid-leaf-1", "uuid-leaf-2", "uuid-leaf-3"] }

الفكرة الجوهرية: هذا المسار يستقبل القائمة الكاملة المطلوبة نهائياً، والباك إند يحسب الفرق (إضافة/حذف) بنفسه.

القاعدةماذا يعني هذا للفرونت
ممنوع إرسال قسم رئيسي (جذر)لا Checkbox على مستوى القسم الرئيسي
ممنوع إرسال قسم متوسط (له أبناء)الاختيار مفعّل فقط عند العقد التي is_leaf = true
الجذر الأكبر للفرع يجب أن يكون مفعّلاً للمتجر مسبقاًغير ذلك يرجع 403 مع اسم القسم

استجابة التعارض

HTTP 422
{
  "success": false,
  "requires_transfer": true,
  "message": "التصنيف الذي تحاول إزالته يحتوي على منتجات بمتجرك..."
}
⚠️ الباك إند لا يخبرك بأي تصنيف بالتحديد فيه التعارض احسب بنفسك removedLeafIds = originalCategoryIds - newSelectedCategoryIds قبل الإرسال، واحتفظ بها في الحالة — ستحتاجها في الخطوة 2.

5. الخطوة 2 — جلب الأشقاء المتاحين

GET /categories/Targets/{CategoryId}

{CategoryId} هنا هو أحد عناصر removedLeafIds التي حسبتها في الخطوة 1.

{ "success": true, "data": [ { "id": "uuid", "name": "قمصان رسمية" } ] }
⚠️ الفخ الأخطر في العملية كلها هذا المسار لا يعيد كل إخوة القسم من الكتالوج العام — بل فقط الإخوة الذين التاجر نفسه أضافهم مسبقاً لمتجره وهم أوراق أيضاً. قد ترجع data: [] فارغة رغم وجود إخوة كثر في الكتالوج العام. هذا قيد عمل متعمد، وليس خطأ من الفرونت.
توصية للحالة الفارغة اعرض رسالة: "لا يوجد قسم فرعي بديل مضاف لمتجرك تحت نفس القسم الرئيسي. أضف قسماً آخر أولاً." ولا تسمح بحقل إدخال يدوي لمعرّف القسم الجديد.

6. الخطوة 3 — تنفيذ النقل الفعلي

POST /categories/Transfer
{ "old_category_id": "uuid", "new_category_id": "uuid" }

ينقل كل منتجات المتجر من القسم القديم للجديد، ويحذف القديم من قائمة تصنيفات المتجر — كل هذا داخل معاملة واحدة غير قابلة للتراجع.

بعد النجاح أعد جلب بروفايل المتجر (getProfile) لتحديث الحالة المحلية، بدلاً من التعديل اليدوي على القائمة.

8. نصائح عملية لتفادي الاحتكاك مع الباك إند

  1. لا تُرسل أبداً IDs لأقسام رئيسية أو متوسطة — عطّل الـ Checkbox فعلياً وليس فقط بصرياً.
  2. لا تحسب الفرق بنفسك لإرساله — أرسل دائماً القائمة الكاملة، الباك إند يقارن.
  3. احتفظ بنسخة أصلية (snapshot) من category_ids فور تحميل البروفايل لحساب removedLeafIds لاحقاً.
  4. تعامل مع GET /Targets/{id} دائماً كاستجابة قد تكون فارغة، واعرض حالة فارغة واضحة.
  5. أعد جلب بروفايل المتجر بعد أي Transfer ناجح بدلاً من التعديل اليدوي محلياً.
  6. مساري المشتري والتاجر منفصلان تماماً في الباك إند — لا تشارك الكاش بينهما رغم تشابه شكل البيانات.

9. ملاحظة مقترحة لفريق الباك إند

استجابة 422 ترجع requires_transfer: true بدون قائمة IDs المتعارضة فعلياً. لو أضاف الباك إند حقل conflicting_category_ids سيوفر ذلك على الفرونت حساب الفرق يدوياً بالكامل.
