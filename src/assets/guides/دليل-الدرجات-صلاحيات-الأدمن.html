دعم الدرجات (Shades) — بعد تقييد الصلاحيات للأدمن فقط

هذا الدليل محدَّث بناءً على مسارات admin.php وSeller.php الفعلية: إدارة كتالوج الدرجات (إضافة/تعديل/حذف) أصبحت حصراً عند الأدمن، والتاجر أصبح بوضع قراءة فقط. الشرح موجّه لفريقي Flutter (تطبيق المشتري وتطبيق التاجر على الهاتف) وAngular (لوحة تحكم الأدمن ولوحة التاجر على الويب).

لا يوجد كود فعلي كامل غير مسارات الـ Controllers وصلني ملفا المسارات فقط (بدون أجسام الدوال داخل الـ Controllers نفسها)، إضافة لتوثيق API سابق. بنيت هذا الدليل على تقاطع الاثنين. أي فحص صلاحية إضافي داخل جسم الدالة (مثال: تحقق ملكية دقيق) غير مضمون هنا ويحتاج تأكيد من الباك إند.

تصفح المشتري — صفحة المنتج

GET/api/Buyer/products/{slug}

الاستجابة تتضمن data.shades[] عند وجود درجات. كل درجة تحمل صورها الخاصة داخل shades[].images.

{
  "data": {
    "id": "product-uuid",
    "shades": [
      { "id": "shade-uuid-1", "name": "الدرجة الفاتحة",
        "images": [{ "id": "image-uuid", "image_url": "...", "is_primary": true }] }
    ],
    "colors": [], "sizes": []
  }
}
لا يجوز إرسال color_id وshade_id معاً نفس عنصر السلة أو نفس الصورة لا يقبل الاثنين معاً. إن كان المنتج يتطلب اختياراً، يجب تعطيل زر "إضافة للسلة" حتى يتم الاختيار، والصورة المعروضة تتحدث تلقائياً حسب الدرجة/اللون المختار.

السلة والطلب

POST/api/cart/items
{ "product_id": "...", "quantity": 1, "shade_id": "shade-uuid", "size_id": "size-uuid" }
PUT/api/cart/items/{cartItemId}
GET/api/cart

كل عنصر يحمل shade_id, shade_name, وis_shade_valid. نفس المنتج بمقاس واحد لكن بدرجتين مختلفتين يظهر كعنصرين منفصلين في السلة.

is_shade_valid صار أهم مما كان بما أن حذف الدرجة أصبح بيد الأدمن فقط، وهي عملية على الكتالوج المركزي المشترك بين كل المتاجر، حذف درجة واحدة قد يُبطل عناصر سلة في متاجر متعددة دفعة واحدة. تأكد أن شاشة السلة تتعامل بوضوح مع is_shade_valid: false (تعطيل الشراء + رسالة "الدرجة لم تعد متوفرة") بدل تجاهل الحقل.
POST/api/orders/store

الدرجة تنتقل تلقائياً من عنصر السلة لعنصر الطلب — لا حاجة لإرسالها مجدداً. داخل invoice.items[] تظهر كحقل shade نصي.

التاجر — قراءة فقط

مسارات SellerShadeController تحت /api/store/shades:

الميثودالمسارالوصف
GET/store/shadesقائمة الدرجات (نفس كتالوج الأدمن، بدون تصفية حسب المتجر)
GET/store/shades/{id}تفاصيل درجة واحدة
لا يوجد store/update/delete للتاجر — والخطأ 404 وليس 403 هذا ليس فحص صلاحية يرجع خطأ "غير مصرح" — المسارات نفسها غير معرّفة أصلاً في Seller.php. لو حاول الفرونت إند إرسال POST/PUT/DELETE لهذا المسار (مثلاً كود قديم قبل التحديث) سيرجع 404 Not Found، وليس 403 Forbidden. لا تبني منطق معالجة الخطأ على افتراض 403 لهذه الحالة تحديداً.
تصميم الشاشة بما أن الاختيار للتاجر Read-only، اعرض الدرجات كقائمة اختيار (Select/Autocomplete) فقط بدون أي زر "إضافة درجة جديدة" داخل شاشة التاجر. إن احتاج التاجر درجة غير موجودة، هذا يحتاج تواصل خارج النظام مع الأدمن حالياً — لا مسار لطلبها من داخل التطبيق.

ربط الدرجة بصورة منتج (التاجر ما زال يفعل هذا)

POST/api/store/products/{id}/images

القراءة فقط لا تعني اختفاء الدرجات من شاشة التاجر بالكامل: التاجر ما زال يربط shade_id موجود مسبقاً بصورة منتج عند الرفع — هو فقط لا يستطيع إنشاء درجة جديدة لم تكن موجودة بالكتالوج.

images[0][file]     = image-file
images[0][shade_id] = shade-uuid   // من قائمة GET /store/shades فقط
فخ محتمل بمسار مكرر — راجع مع الباك إند داخل مجموعة prefix('/products') يوجد سطر: Route::post('/products/{id}/general-images', ...) — بما أنه بالفعل داخل بادئة /products، فالمسار الفعلي الناتج هو /store/products/products/{id}/general-images (كلمة products مكررة). قبل استخدام هذا المسار في الفرونت إند تأكد من الباك إند إن كان هذا مقصوداً أو خطأ كتابي.

نصائح عملية لتفادي الاحتكاك مع الباك إند

  1. لا تبني أي زر إضافة/تعديل/حذف درجة داخل شاشات التاجر — هذه المسارات غير موجودة له إطلاقاً، الإخفاء يجب أن يكون من الفرونت لا انتظار خطأ من السيرفر.
  2. وحّد مكوّن "قراءة فقط" الواحد بين الدرجات والألوان والمقاسات عند التاجر، فالثلاثة تتبع نفس بنية index / show فقط.
  3. عند بناء لوحة الأدمن، وحّد مكوّن CRUD واحد قابل لإعادة الاستخدام للدرجات/الألوان/المقاسات لتطابق بنية المسارات الخمس المتماثلة.
  4. تحقق دائماً من is_shade_valid في استجابة السلة قبل السماح بإتمام الطلب.
  5. امنع إرسال color_id وshade_id معاً من واجهة الإدخال نفسها (راديو مشترك) بدل الاعتماد على رفض السيرفر.

ملاحظة مقترحة لفريق الباك إند

مسار general-images مكرر البادئة في Seller.php، السطر Route::post('/products/{id}/general-images', ...) معرّف داخل prefix('/products') أصلاً، فينتج مسار /store/products/products/{id}/general-images. الرجاء التأكيد إن كان مقصوداً أو تصحيحه لـ /store/products/{id}/general-images قبل اعتماد الفرونت إند عليه رسمياً.
حذف درجة مركزية بلا فحص استخدام بما أن DELETE /admin/shades/{id}/delete يحذف من كتالوج مشترك بين كل المتاجر، يُقترح فحص استخدام الدرجة الحالي (سلات مفتوحة، منتجات منشورة) قبل الحذف الفعلي، أو اعتماد حذف ناعم (Soft Delete) بدل الحذف النهائي.
دليل داخلي لفريق الفرونت إند — مبني على مسارات admin.php وSeller.php وتوثيق API الحالي لدعم الدرجات.
