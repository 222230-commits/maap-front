Reports Module · v1

دليل ربط الفرونت إند — نظام البلاغات

يوجد 3 Controllers منفصلة تماماً تتشارك نفس جدول reports لكنها معزولة بالكامل من ناحية النطاق (Scope) والصلاحيات: الأدمن يرى كل شيء، بينما المشتري والتاجر كل منهما يرى فقط البلاغات التي قدّمها هو بنفسه — وليس البلاغات المُقدَّمة ضده. هذا الفرق الجوهري يجب أن ينعكس في تصميم الواجهة قبل أي شيء آخر.

⚠
فخّ مفاهيمي مهم: مسار /store/reports و /Buyer/reports ليسا "صندوق وارد بلاغات عن حسابي/متجري" — بل "سجل البلاغات التي أرسلتُها أنا كمُبلِّغ". لا يوجد حالياً في الكود المرفق أي Endpoint يعرض للتاجر البلاغات المُقدَّمة ضد متجره أو منتجاته؛ تلك تُدار حصراً من طرف الأدمن.

⚠
فخّ #5 — طبقتان مختلفتان تماماً من 429: الأولى من throttle:3,1 (ميدل وير Laravel القياسي) وتُطلَق قبل وصول الطلب للكونترولر أصلاً — شكل استجابتها لا يطابق غلاف {success, message} المعتاد (عادة {"message":"Too Many Attempts."} بدون success)، وتحمل هيدر Retry-After. أما 429 الثانية فمن منطق الكونترولر نفسه (حد الـ 3 يومياً) وتتبع الغلاف الموحّد. يجب على الفرونت التحقق من وجود مفتاح success في جسم الاستجابة لتحديد أي رسالة يعرضها للمستخدم، بدل افتراض شكل واحد لكل 429.
⚠
حظر "البلاغ المكرر" (آخر خطوة) يتحقق فقط من الحالة pending. إذا سبق أن أُغلق بلاغ سابق لنفس العنصر (محلول/مرفوض)، يُسمح للمستخدم بإعادة الإبلاغ عنه من جديد — لا تُبنِ منطق "زر الإبلاغ" على افتراض أنه يُعطَّل نهائياً بعد أول بلاغ.

الربط في Flutter — مع معالجة الطبقتين من 429

Future<Report> submitReport({
  required String targetType, required String targetId, required String reason,
}) async {
  try {
    final res = await _dio.post('/Buyer/reports/store', data: {
      'target_type': targetType, 'target_id': targetId, 'reason': reason,
    });
    return Report.fromJson(res.data['data']);
  } on DioException catch (e) {
    final body = e.response?.data;
    final hasEnvelope = body is Map && body.containsKey('success');
    if (e.response?.statusCode == 429) {
      throw ReportException(hasEnvelope
        ? body['message']
        : 'محاولات كثيرة خلال دقيقة واحدة، أعد المحاولة بعد قليل.');
    }
    if ([422, 404].contains(e.response?.statusCode)) {
      throw ReportException(body['message']);
    }
    rethrow;
  }
}

نصائح عملية لتفادي الاحتكاك مع الباك إند

  1. ابنِ Interceptor واحد (Dio في Flutter / HttpInterceptor في Angular) يفحص وجود مفتاح success في كل خطأ 4xx/5xx قبل قراءة message — لتفادي كسر التطبيق عند 429 من Laravel نفسه.
  2. لا تبني عدّاد "بلاغات متبقية اليوم" أو "بلاغات معلّقة متبقية" من نص رسالة الخطأ — احسبه من stats.pending في استجابة index الخاصة بالمستخدم نفسه قبل فتح فورم الإبلاغ، وعطّل الزر استباقياً.
  3. لا تشارك أي Cache/State واحد بين شاشة "بلاغاتي كمشتري" و"بلاغاتي كتاجر" حتى لو كان المستخدم نفسه يملك الحسابين — الـ Endpoints منفصلة تماماً بالخلفية ولا تتشارك نفس النطاق.
  4. في نموذج الإبلاغ، قيّد Dropdown نوع البلاغ (Enum) حسب سياق التطبيق (4 خيارات للمشتري، 3 فقط للتاجر بدون "متجر") بدل عرض قائمة موحّدة يرفضها السيرفر لاحقاً.
  5. حالة investigating (لدى الأدمن) أصبحت الآن مُعادة صراحة ضمن stats — اعرضها كشارة/عمود مستقل عن pending/resolved/dismissed في أي رسم بياني أو عدّاد، ولا تُدرجها ضمن "معلّقة" افتراضياً رغم تشابه المعنى الظاهري.
