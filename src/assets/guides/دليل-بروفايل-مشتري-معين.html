دليل بروفايل مشتري معين

جلب بروفايل مشتري معين (Public Profile)

GET /Buyer/profile/{buyer}

{buyer} هو معرّف (ID) أي مستخدم في النظام — وليس بالضرورة المستخدم الحالي المسجّل دخوله. يُستخدم هذا المسار لعرض بروفايل مستخدم آخر (مثلاً عند الضغط على اسم كاتب تعليق في شاشة التقييمات، أو عند عرض من يتابع متجراً معيناً).

مثال الاستجابة — 200
{
  "message": "تم جلب البروفايل العام للمشتري بنجاح.",
  "data": {
    "personal_info": {
      "id": "uuid",
      "full_name": "مها أحمد",
      "avatar_url": "https://...",
      "joined_at": "2024-03-10"
    },
    "statistics": {
      "total_orders": 32,
      "total_reviews_written": 9,
      "followed_shops_count": 5
    }
  }
}
استجابة الخطأ — 403 (محاولة عرض بروفايل حساب إدارة)
{
  "error": "لا يمكن عرض بروفايل الإدارة"
}
الحقلالوصف
personal_info.joined_atتاريخ فقط بصيغة YYYY-MM-DD بدون وقت — يكون null إن لم يوجد تاريخ إنشاء لسبب ما
statistics.total_ordersإجمالي عدد الطلبات التي قام بها هذا المشتري (كل الحالات، وليس المكتملة فقط)
statistics.total_reviews_writtenعدد التقييمات التي كتبها هذا المستخدم على منتجات مختلفة
statistics.followed_shops_countعدد المتاجر التي يتابعها
⚠ statistics يحتوي الآن ثلاثة حقول فقط: total_orders، total_reviews_written، وfollowed_shops_count. حقل wishlist_items_count (عدد منتجات المفضلة) لم يعد موجوداً في هذه الاستجابة — لا تعتمد عليه إن كنت قد بنيت الواجهة على نسخة سابقة من هذا الدليل. إن كانت شاشتك تعرض عدد عناصر المفضلة لمستخدم آخر، يجب إزالة ذلك العنصر من التصميم أو التنسيق مع الباك إند حول سبب الحذف (انظر "ملاحظة لفريق الباك إند" أدناه).

لماذا لا يظهر رقم الهاتف أو البريد الإلكتروني؟

✓ هذا متعمّد وليس نقصاً في الكود. لاحظ في الاستجابة أعلاه أن personal_info يحتوي فقط أربعة حقول مُختارة يدوياً: id، full_name، avatar_url، وjoined_at. الكود لا يستخدم $buyer->toArray() أو ما شابه (ما كان سيُخرج كل أعمدة الجدول بما فيها الهاتف والبريد)، بل يبني مصفوفة يدوية تحتوي فقط الحقول الآمنة للعرض العام. هذا هو نمط "القائمة البيضاء" (Whitelisting) لحماية خصوصية المستخدمين — أي بيانات تواصل حساسة لا تدخل الاستجابة من الأساس، فلا داعي لإخفائها لاحقاً في الفرونت.
⚠ هذا المسار مخصص لعرض بروفايل مستخدم آخر (Public Profile)، وهو مختلف تماماً عن مسار "بروفايلي الشخصي" (GET /user/profile/Show) الذي يعيد بيانات المستخدم المسجّل دخوله هو نفسه، والذي من المتوقع أن يحتوي حقولاً حساسة مثل الهاتف والبريد والعنوان لأنه يعرض بيانات صاحب الحساب لنفسه فقط. لا تخلط بين المسارين: لا تستخدم بيانات هذا المسار العام لملء نموذج "تعديل الملف الشخصي" الخاص بالمستخدم الحالي — استخدم مسار البروفايل الخاص فقط لذلك.
⚠ التحقق الوحيد المطبَّق في هذا المسار هو استبعاد الحسابات ذات role = admin (يرجع 403). لا يوجد تحقق من أن المستخدم المطلوب عرضه هو "مشترٍ" فعلاً بمعنى الكلمة — أي حساب تاجر (Seller) غير إداري يمكن أيضاً عرض بروفايله عبر هذا المسار بنفس الشكل بالضبط. لا تفترض أن كل نتيجة تُعاد من هنا هي بالضرورة "مشترٍ" فقط.

قائمة المتاجر المتابَعة لمشترٍ معيّن

GET /Buyer/profile/{buyer}/followed-shops?per_page=10

يعيد قائمة مُرقّمة (Paginated) بالمتاجر التي يتابعها {buyer}، مرتبة بتاريخ المتابعة الأحدث أولاً.

استجابة الخطأ — 403 (محاولة عرض متابَعات حساب إدارة)
{
  "error": "لا يمكن عرض بروفايل الإدارة"
}
شكل الاستجابة الفعلي — انتبه جيداً للتعشيش
{
  "message": "تم جلب المتاجر المُتابَعة للمشتري بنجاح.",
  "data": {
    "current_page": 1,
    "data": [
      {
        "id": "uuid",
        "name": "متجر الأناقة",
        "logo_url": "https://...",
        "slug": "elegance-store",
        "followed_at": "2026-06-01"
      },
      {
        "id": "uuid",
        "name": "متجر التقنية",
        "logo_url": null,
        "slug": "tech-store",
        "followed_at": "2026-05-12"
      }
    ],
    "first_page_url": "...",
    "from": 1,
    "last_page": 3,
    "last_page_url": "...",
    "links": [ "..." ],
    "next_page_url": "...",
    "path": "...",
    "per_page": 10,
    "prev_page_url": null,
    "to": 10,
    "total": 25
  }
}
⚠ هذا هو الفخ الأهم في هذا المسار: كلمة data تظهر في الاستجابة على مستويين بمعنيين مختلفين تماماً. data الخارجي (بجانب message) هو كائن ترقيم الصفحات (Paginator) بأكمله بكل حقوله (current_page, links, meta...)، بينما data الداخلي (داخل ذلك الكائن) هو المصفوفة الفعلية لعناصر المتاجر. أي محاولة قراءة response.data مباشرة كأنها مصفوفة متاجر ستفشل أو تُرجع كائناً غير متوقع — الوصول الصحيح للعناصر هو response.data.data، ورقم الصفحة الحالية هو response.data.current_page، وهكذا. هذا الشكل مختلف تماماً عن نمط الترقيم المستخدم في مسارات التقييمات (حيث data هي المصفوفة مباشرة و meta/links منفصلان على نفس المستوى) — لا تُطبّق نفس دالة قراءة الترقيم من هناك على هذا المسار.
⚠ followed_at هنا تاريخ فقط (بدون وقت)، بعكس created_at_human/created_at الكاملين المستخدَمين في مسارات أخرى مثل التقييمات. لا تتوقع دقة بالساعة والدقيقة لوقت المتابعة.

جدول ملخّص لكل الأخطاء المتوقعة

الكوديظهر فيالمعنىماذا يفعل الفرونت
401 كلا المسارين لا يوجد توكن صالح للمستخدم الحالي أعد المستخدم لشاشة تسجيل الدخول
403 كلا المسارين (profile و followed-shops) المعرّف المطلوب يخص حساب إدارة (role = admin) اعرض رسالة "هذا البروفايل غير متاح" بدل رسالة خطأ عامة
404 (Route Model Binding) كلا المسارين معرّف {buyer} غير موجود في النظام اعرض شاشة "المستخدم غير موجود" العامة

نصائح عملية لتفادي الاحتكاك مع الباك إند

  1. لا تعرض حقول هاتف أو بريد إلكتروني في شاشة بروفايل مستخدم آخر — هذه البيانات غير موجودة أصلاً في الاستجابة، وعرضها كـ "فارغة" بدل إخفاء العنصر بالكامل يعطي انطباعاً خاطئاً بأن البيانات وُجدت ولكنها فارغة.
  2. عند قراءة قائمة المتاجر المتابَعة، تعامل مع response.data كـ كائن ترقيم صفحات كامل، واستخرج المصفوفة من response.data.data تحديداً — لا تُطبّق منطق القراءة نفسه المستخدَم في مسارات التقييمات لأن شكل الترقيم مختلف هناك.
  3. ميّز دائماً بين مسار "بروفايلي أنا" (بيانات كاملة، حساسة) ومسار "بروفايل شخص آخر" (بيانات عامة محدودة) في الكود، حتى لو تشابهت التسميات — لا تستخدم نفس النموذج (Model class) في الفرونت لكليهما دون تمييز واضح للحقول المتاحة.
  4. اربط الانتقال لهذه الشاشة من أي مكان يظهر فيه اسم مستخدم آخر قابل للنقر (كاتب تعليق، متابع لمتجر) عبر {buyer} الخاص به، وليس عبر بيانات محلية مخزَّنة مسبقاً قد تكون قديمة.

ملاحظة مقترحة لفريق الباك إند

⚠ showSpecificBuyer يستبعد صراحة الحسابات ذات role = admin برسالة 403 واضحة، بينما buyerFollowedShops لا يحتوي أي فحص مشابه إطلاقاً — يمكن لأي مستخدم مسجّل دخول حالياً جلب قائمة المتاجر التي يتابعها حساب إداري عبر GET profile/{admin_id}/followed-shops مباشرة، رغم منع الوصول لبروفايله الأساسي. يُقترح توحيد نفس فحص الاستبعاد في بداية buyerFollowedShops إن كان هذا غير مقصود.
⚠ حقول statistics (خصوصاً total_orders وwishlist_items_count) تُعرض حالياً لأي مستخدم آخر عبر هذا المسار العام، دون فحص خصوصية إضافي. يُستحسن التأكيد مع فريق المنتج ما إذا كان عرض عدد طلبات ومفضلة مستخدم آخر لأي زائر مسجّل دخول قراراً مقصوداً، أم يجب حصره بالمستخدم نفسه فقط (وعرض عدد التقييمات والمتابعات فقط للعموم بصفتها معلومات اجتماعية غير حساسة).
