دليل ربط الفرونت إند بنظام الطلبات (Buyer & Seller Orders)

هذا الدليل يغطي جميع مسارات الطلبات الخاصة بالمشتري والتاجر: شكل كل طلب واستجابة، قواعد العمل غير الظاهرة من اسم الدالة، والفخاخ التي يجب الانتباه لها قبل البناء عليها، بالإضافة لتصميم مقترح للشاشات الرئيسية وربطها بكل Endpoint.

1. قائمة طلبات المشتري

GET /Buyer/orders?tab=pending&per_page=10&page=1

يتطلب مصادقة auth:sanctum. لا يوجد Body — فقط Query Params اختيارية: tab و per_page و page.

مثال الاستجابة

{
  "success": true,
  "tabs_count": {
    "all": 24,
    "pending": 3,
    "waiting_buyer": 2,
    "preparing": 5,
    "awaiting": 1,
    "completed": 12,
    "cancelled": 1
  },
  "data": {
    "current_page": 1,
    "data": [ { "id": "...", "status": "pending", "shop": {...}, "items": [...] } ],
    "last_page": 3,
    "per_page": 10,
    "total": 24
  }
}
فخ: عداد التاب المدمج ليس مُجمّعاً مسبقاً التاب المعروض للمستخدم هو "قيد الانتظار" ويضم فعلياً حالتي pending و waiting_buyer معاً (هذا واضح من منطق الفلترة: عند إرسال tab=pending يتم جلب الحالتين معاً). لكن tabs_count يعيدهما كحقلين منفصلين ولا يعيد رقماً مُجمّعاً جاهزاً باسم "قيد الانتظار". يجب على الفرونت جمع pending + waiting_buyer بنفسه ليطابق الرقم الفعلي الذي سيحصل عليه عند فتح ذلك التاب.
فرق عن نفس الميزة عند التاجر مسار التاجر المكافئ (أدناه) يعيد الرقم المدمج جاهزاً تحت مفتاح new. أي أن نفس الفكرة (دمج حالتين تحت تاب واحد) مُنفّذة بطريقتين مختلفتين بين شاشتي المشتري والتاجر — لا تفترض أن الكود قابل لإعادة الاستخدام بينهما بدون تعديل.

3. إنشاء الطلب من السلة

POST /Buyer/orders/store

Request Body

{
  "shop_id": "uuid",
  "shipping_address": { "city": "...", "street": "..." },
  "payment_method": "Cash on Delivery"
}
الحقلالقاعدة
shop_idمطلوب، uuid، exists:shops
shipping_addressمطلوب — يقبل نصاً أو كائن JSON، لا يوجد تحقق من الشكل الداخلي
payment_methodمطلوب، من: Cash on Delivery / Credit Card / Wallet

استجابة النجاح 201

{ "success": true, "message": "تم إنشاء الطلب بنجاح.", "data": [ { "id": "...", "status": "pending", ... } ] }

استجابة خطأ عمل (Business) 400

{ "success": false, "message": "لديك 5 طلبات مفتوحة، يرجى استكمالها أو إلغاؤها أولاً." }

استجابة خطأ غير متوقع 500

{ "success": false, "message": "حدث خطأ غير متوقع أثناء إتمام الطلب.", "error": null }
فخ: data دائماً مصفوفة وليست كائناً واحداً رغم أن الطلب مرتبط بمتجر واحد (shop_id) وأن سلة الشراء المُمرَّرة للخدمة مُفلترة مسبقاً لهذا المتجر فقط، فإن الكود الداخلي يُعيد تجميع العناصر حسب المتجر من جديد (groupBy shop_id) وينشئ مصفوفة طلبات. النتيجة عملياً عنصر واحد دائماً حالياً، لكن شكل الاستجابة مصفوفة — تعامل مع data[0] ولا تتوقع كائناً مفرداً، خصوصاً إن تغيّرت منطق التجميع مستقبلاً لدعم سلة متعددة المتاجر في نفس الطلب.
قائمة الأسباب التي تُرجع 400 كثيرة ومتنوعة من بينها: تجاوز 5 طلبات مفتوحة، حظر مؤقت للمستخدم بسبب تجاوز حد الإلغاءات، السلة فارغة لهذا المتجر، منتج غير متاح أو نُشر لاحقاً، نقص المخزون، لون أو مقاس لم يعد متوفراً، أو رفض المتجر للدفع بالبطاقة الائتمانية. جميعها تصل بنفس الشكل (success:false + message نصي فقط بدون كود مميز) — يجب عرض الرسالة كما هي للمستخدم وليس بناء منطق قرار عليها، لأنه لا يوجد حقل error_code يمكن الاعتماد عليه للتفريق برمجياً بين الأسباب.
الحظر التلقائي للمشتري لا يظهر إلا لاحقاً إذا تجاوز الزبون 7 عمليات إلغاء (لأسباب خاصة به، ما عدا الإلغاء بسبب نقص المخزون) خلال 30 يوماً، يُحظر تلقائياً من الطلب لمدة 14 يوماً. لا تصل أي إشارة لهذا الحظر في استجابة الإلغاء نفسه — سيكتشفه المستخدم فقط عند محاولة إنشاء طلب جديد لاحقاً ويحصل على رسالة حظر. يُستحسن للفرونت عرض تنبيه استباقي عند اقتراب المستخدم من هذا الحد إن توفر مصدر بيانات لذلك مستقبلاً.

فخ: تسمية مختلفة لنفس المفهوم بين هذا المسار ومسار checkout-preview هنا اسم المنتج product_title، بينما في checkout-preview نفس المفهوم اسمه product_name. لا تشارك أي دالة عرض/تحويل (mapper) واحدة بين الشاشتين بافتراض تطابق أسماء الحقول.

اللون والمقاس هنا Snapshot ثابت color و size يُقرآن من لقطة محفوظة وقت إنشاء الطلب وليس من بيانات المنتج الحالية، لذا ستبقى صحيحة حتى لو عدّل التاجر ألوان/مقاسات المنتج لاحقاً.

5. رد الزبون على طلب جزئي التوفر

POST/Buyer/orders/{order}/respond-review
{ "accept": true }
{ "success": true, "message": "تم اعتماد الطلب للمنتجات المتوفرة." }
فخ: لا يوجد try/catch حول هذا المسار استدعاء الخدمة هنا غير مغلّف بمعالجة استثناءات في الـ Controller. إن حاول مشتري آخر غير مالك الطلب الوصول لهذا المسار، أو أُرسل الطلب وهو ليس بحالة تتطلب موافقة (requires_buyer_approval = false)، فسيرمي الكود استثناء BusinessException لن يُلتقط هنا، والنتيجة صفحة خطأ خادم قياسية (غير JSON منسّق بـ success/message) بدل استجابة نظيفة 400/403. يجب على الفرونت عدم الاعتماد على شكل {success:false} لهذا المسار تحديداً عند التعامل مع الفشل، والتعامل مع أي استجابة غير JSON كخطأ عام.
الإجمالي يُعاد حسابه تلقائياً عند القبول الجزئي total_price يُعاد احتسابه بالخادم بناءً على العناصر المتوفرة فقط — لا تعرض للمستخدم مجموعاً محسوباً في الفرونت من قبل، بل اطلب الفاتورة المحدثة عبر GET /orders/{id} بعد الرد.

6. تأكيد استلام الطلب

POST/Buyer/orders/{order}/confirm-receipt
{ "success": true, "message": "تم تأكيد الاستلام بنجاح، شكراً لك." }
فخ: عملية نهائية غير قابلة للتراجع + لا يوجد try/catch بعد هذا الاستدعاء تتحول الحالة إلى completed نهائياً — لا يوجد مسار رجوع أو إلغاء بعدها في الكود. تأكد من وجود تأكيد صريح (نافذة "هل أنت متأكد؟") قبل الاستدعاء. كذلك هذا المسار غير مغلّف بمعالجة استثناءات، فمحاولة التأكيد على طلب ليس بحالة awaiting أو لا يخص المستخدم سترمي خطأ غير منسّق (وليس JSON نظيفاً).

7. إلغاء الطلب (من المشتري)

POST/Buyer/orders/{order}/cancel
{ "reason": "غيّرت رأيي" }
{ "success": true, "message": "تم إلغاء الطلب." }
فخ مكرر: نفس غياب معالجة الاستثناءات محاولة إلغاء طلب مكتمل بالفعل أو ملغي سابقاً سترمي BusinessException غير مُلتقطة هنا أيضاً → استجابة غير منسّقة. يُستحسن أن يُخفي الفرونت زر "إلغاء" أصلاً عن أي طلب بحالة completed أو cancelled لتفادي الوصول لهذا المسار أصلاً بدل الاعتماد على رسالة خطأ نظيفة من الخادم.
هذا الإلغاء قد يُحتسب ضمن حد الحظر كل إلغاء من هذا المسار (بسبب غير نقص المخزون) يُحسب ضمن عداد الإلغاءات الشهري الذي قد يؤدي لحظر 14 يوماً عند تجاوز 7 مرات. راجع الفخ في قسم "إنشاء الطلب" أعلاه.

8. قائمة طلبات المتجر (للتاجر)

GET/store/orders?tab=new
{
  "success": true,
  "tabs_count": { "all": 40, "new": 5, "preparing": 8, "awaiting": 2, "completed": 24, "cancelled": 1 },
  "data": { "current_page": 1, "data": [...], "per_page": 15, "total": 40 }
}
هنا العد مُجمّع مسبقاً مفتاح new يمثل مجموع pending + waiting_buyer جاهزاً من الخادم (بعكس شاشة المشتري في القسم 1). لا حاجة لأي جمع يدوي هنا.
عدد العناصر بالصفحة ثابت هنا: 15 بعكس مسار المشتري الذي يقبل per_page اختياري، هذا المسار يتجاهل أي قيمة تُرسل من الفرونت ويستخدم 15 دائماً — لا تبني منطق ترقيم (pagination) في الواجهة بافتراض إمكانية التحكم بحجم الصفحة.
404 بدون status code JSON منسق دائماً، لكن هذه الحالة نفسها منسّقة فعلاً إن لم يملك المستخدم الحالي متجراً (shop = null) يعيد الكود JSON نظيفاً بحالة 404 ورسالة "متجر غير موجود." — وهذه حالة متسقة، لكنها الاستثناء الوحيد المنسق ضمن كل مسارات التاجر كما سترى أدناه.

{ "success": true, "message": "تم مراجعة الطلب وجميع المنتجات متوفرة (انتقل إلى قيد التجهيز)." }

// بعض العناصر غير متوفرة

// كل العناصر غير متوفرة
{ "success": true, "message": "تم إلغاء الطلب بالكامل لعدم توفر جميع المنتجات." }
فخ: النتيجة الفعلية غير معروفة إلا من نص الرسالة الاستجابة الناجحة لا تعيد الحالة الجديدة للطلب status ولا أي حقل مهيكل يوضح أي سيناريو من الثلاثة تحقق — فقط رسالة نصية موجهة للعرض المباشر للمستخدم. إن احتجت التصرف برمجياً (مثلاً إغلاق المودال أو تحديث شارة الحالة في القائمة)، يجب عليك استدعاء GET /store/orders أو تفاصيل الطلب من جديد بعد نجاح هذا الاستدعاء لمعرفة الحالة الفعلية، ولا تعتمد على تحليل نص الرسالة.
فخ: عدم وجود صلاحية مالكة مرئية في الكود هنا يعتمد على الخدمة فقط التحقق من كون التاجر هو مالك المتجر الفعلي للطلب يتم داخل الخدمة عبر استثناء غير مُلتقط في الـ Controller — أي محاولة تاجر مراجعة طلب لا يخصه سترمي خطأ خادم غير منسّق (وليس 403 نظيفاً كما في مسار الإلغاء أدناه الذي يتحقق صراحة في الـ Controller).
المخزون يُعاد فوراً عند تحديد "غير متوفر" أي عنصر يُحدَّد is_available:false تُعاد كميته للمخزون فوراً ضمن نفس المعاملة، بغض النظر عن قرار الزبون اللاحق. لا تعرض للتاجر أي خيار "تراجع" بعد الإرسال دون إعادة تحميل بيانات المنتج، لأن المخزون يكون قد تغيّر فعلياً.

403 — التاجر لا يملك هذا الطلب

{ "success": false, "message": "غير مصرح لك بإلغاء هذا الطلب." }
هذا المسار الوحيد بين مسارات التاجر الذي يتحقق من الصلاحية بشكل صريح في الـ Controller لذلك هو المسار الوحيد الذي يمكن الاعتماد فيه فعلياً على استجابة JSON منسّقة (403) عند محاولة الوصول لطلب لا يخص التاجر. باقي مسارات التاجر (المراجعة، mark-ready) تعتمد على استثناء داخلي غير مُلتقط لنفس السيناريو.
هذا الإلغاء لا يُحسب على الزبون الإلغاء من طرف التاجر يُسجَّل بعلامة is_seller_fault = true ولا يدخل ضمن عداد الإلغاءات المؤدي لحظر المشتري — بعكس إلغاء المشتري لنفس الطلب.

نصائح عملية لتفادي الاحتكاك مع الباك إند

  1. لا تعتمد على تحليل نص رسائل النجاح لمعرفة النتيجة الفعلية (خصوصاً مسار مراجعة التاجر) — أعد جلب حالة الطلب بعد كل عملية تغيّر الحالة.
  2. أخفِ الأزرار التي تؤدي لمسارات بلا معالجة استثناءات (respond-review, confirm-receipt, cancel, review, mark-ready) إلا عندما تكون حالة الطلب الحالية مطابقة فعلياً لما يقبله المسار، لتفادي الوصول لخطأ خادم غير منسّق.
  3. لا تشارك دالة تحويل بيانات (mapper) واحدة بين استجابة checkout-preview واستجابة show — أسماء الحقول لنفس المفهوم مختلفة بينهما.
  4. احسب عدّاد التاب "قيد الانتظار" عند المشتري يدوياً (pending + waiting_buyer)، وعند التاجر استخدم مفتاح new الجاهز مباشرة.
  5. لا تمرر per_page في قائمة طلبات التاجر — يتم تجاهله دائماً (15 ثابتة).
  6. تعامل مع data في استجابة إنشاء الطلب كمصفوفة دائماً، حتى عند توقع عنصر واحد فقط.
  7. اطلب من المستخدم تأكيداً صريحاً قبل استدعاء confirm-receipt، فهي عملية نهائية بلا رجعة في الكود الحالي.

ملاحظة مقترحة لفريق الباك إند

توحيد معالجة الاستثناءات عبر مسارات الطلبات خمسة من أصل تسعة مسارات (respond-review, confirm-receipt, buyer cancel, seller review, seller mark-ready) لا تُغلّف استدعاء الخدمة بـ try/catch، بعكس مسار store الذي يعالج BusinessException بشكل نظيف. يُقترح تطبيق نفس نمط المعالجة (أو Exception Handler عام على مستوى التطبيق لـ BusinessException) على بقية المسارات، وإضافة حقل error_code ثابت بجانب message ليتمكن الفرونت من التفريق البرمجي بين أنواع الأخطاء دون تحليل النص العربي.
دليل داخلي لفريق الفرونت إند — تم إنشاؤه بواسطة تحليل مباشر لكود Orders Module (Controllers + Service + Routes).
