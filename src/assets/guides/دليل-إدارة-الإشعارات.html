وحدة إدارة الإشعارات (Notifications)

توثيق شامل لربط مسارات الإشعارات بتطبيق Flutter (تجربة المستخدم النهائي) ولوحة Angular (إدارة/عرض داخلي)، مبني على قراءة فعلية لكود NotificationController وNotificationService وFirebaseService وأوامر الجدولة المرتبطة.

هذا التدفق يوضح ما يحدث فعلياً عند تشغيل orders:auto-complete أو orders:remind-awaiting، وأين ينقطع التدفق قبل الوصول لـ Firebase.

3. قائمة إشعارات المستخدم

GET/notifications?per_page=15

لا يوجد Body للطلب. Query param اختياري: per_page (افتراضي 15، الحد الأقصى 50، أي قيمة ≤0 تُستبدل بـ 15).

مثال استجابة النجاح

{
  "success": true,
  "pagination": {
    "total": 42,
    "current_page": 1,
    "last_page": 3
  },
  "data": [
    {
      "id": "...",
      "type": "order_reminder",
      "notifiable_type": "user",
      "notifiable_id": "...",
      "order_id": "1042",
      "data": { "title": "تذكير بتأكيد استلام الطلب", "body": "طلبك رقم #1042 جاهز للاستلام..." },
      "locale": "ar",
      "read_at": null,
      "created_at": "...",
      "updated_at": "..."
    }
  ]
}
الحقلملاحظة
data.title / data.bodyنص الإشعار الفعلي — لا يوجد حقل title/body top-level منفصل
order_idحقل top-level منفصل، غير مكرر داخل data
read_atnull يعني غير مقروء — استخدمه لتحديد الحالة، لا يوجد حقل is_read منفصل
فخ: استجابة pagination لا تُرجع per_page المُستخدم فعلياً ولا روابط next/prev. الفرونت يجب أن يحتفظ بقيمة per_page التي أرسلها بنفسه لحساب الصفحة التالية بدقة.
فخ: حقل type نص حر مفتوح (القيم المعروفة حالياً: order_reminder, order_auto_completed) وقد يُضاف له قيم جديدة من الباك إند مستقبلاً دون تنسيق مسبق. اجعل أيقونة/تصنيف افتراضي (fallback) لأي type غير معروف بدل الاعتماد على قائمة ثابتة.

4. عدد الإشعارات غير المقروءة

GET/notifications/unread-count
{ "success": true, "unread_count": 5 }
فخ دقيق: هذا المسار وحده لا يُطابق notifiable_type = 'user'، بعكس باقي المسارات. لا تأثير حالياً لأن النوع الوحيد المستخدم هو user، لكن إن أضاف الباك إند لاحقاً إشعارات لأنواع أخرى (متجر/مشرف) فقد يظهر عدد غير دقيق دون سابق إنذار — راقب هذا السلوك.

5. تحديد إشعار واحد كمقروء

PATCH/notifications/{id}/read
// نجاح 200
{ "success": true, "message": "تم تحديد الإشعار كمقروء." }

// فشل 404 — غير موجود أو ليس ملكاً للمستخدم
{ "success": false, "message": "الإشعار غير موجود." }
فخ: لا تُعاد بيانات السجل المُحدَّث. حدّث الحالة محلياً (optimistic update) في الواجهة فور نجاح الطلب بدل انتظار كائن من الاستجابة.

6. تحديد كل الإشعارات كمقروءة

POST/notifications/mark-all-read
{ "success": true, "message": "تم تحديد جميع الإشعارات كمقروءة." }
فخ: الاستجابة نجاح دائماً حتى لو لم يوجد أي إشعار غير مقروء أصلاً — لا يُرجَع عدد السجلات المتأثرة، فلا تعتمد على هذا الرقم لأي منطق عرض.

7. حذف إشعار محدد

DELETE/notifications/{id}/delete
// نجاح 200
{ "success": true, "message": "تم حذف الإشعار بنجاح." }

// فشل 404
{ "success": false, "message": "الإشعار غير موجود أو لا تملك صلاحية حذفه." }
عملية غير قابلة للتراجع: حذف نهائي (hard delete) من قاعدة البيانات، لا يوجد Soft Delete أو سلة محذوفات.

8. مسح جميع الإشعارات

DELETE/notifications/clear-all
{ "success": true, "message": "تم مسح جميع الإشعارات بنجاح." }
عملية غير قابلة للتراجع وجماعية: تحذف كل إشعارات المستخدم دفعة واحدة بلا تأكيد من الباك إند. التأكيد يجب أن يحدث بالكامل على مستوى الفرونت إند (مودال تأكيد إلزامي) قبل استدعاء هذا المسار.

11. نصائح عملية لتفادي الاحتكاك مع الباك إند

  1. لا تبني أي منطق على وصول Push فعلي حالياً — اعتمد على polling/refresh حتى يُعدَّل sendToUser.
  2. اقرأ نص الإشعار دائماً من data.title/data.body، وorder_id من الحقل top-level المنفصل.
  3. عامل حذف الإشعار الفردي والجماعي كعمليات نهائية — أضف تأكيداً في الفرونت حتى لو بدت العملية بسيطة.
  4. حدّث القوائم محلياً بعد mark-as-read / mark-all-read، فلا تنتظر كائناً محدَّثاً من الاستجابة.
  5. تعامل مع type كقيمة مفتوحة قابلة للتوسع — لا تفترض قائمة ثابتة من الأنواع.
  6. احتفظ بقيمة per_page التي أرسلتها بنفسك لحساب الصفحات، فالاستجابة لا تعيدها.

12. ملاحظة مقترحة لفريق الباك إند

1. تفعيل الإرسال الفعلي عبر Firebase: إزالة أو نقل سطر return; في NotificationService::sendToUser بعد الحفظ في قاعدة البيانات، حتى يصل فعلياً كود جلب التوكنز واستدعاء FirebaseService::sendMultiple.
2. لا يوجد مسار لتسجيل FCM Token: النظام يعتمد على جدول app.user_device_tokens ودالة app.get_user_active_tokens، لكن لا يوجد Route مُرسَل ضمن هذه المجموعة لاستقبال/تحديث توكن الجهاز من التطبيق (عادة عند تسجيل الدخول أو فتح التطبيق لأول مرة). بدون هذا المسار لن تُملأ الجداول أصلاً حتى بعد إصلاح النقطة الأولى.
3. توحيد فلترة notifiable_type: unreadCount() لا تُطابق notifiable_type = 'user' بعكس باقي الدوال في نفس الكلاس — يُفضّل التوحيد تحسباً لإضافة أنواع مستقبلية.
دليل تقني داخلي — تم إنشاؤه من تحليل مباشر لكود NotificationController وNotificationService وFirebaseService وأوامر الجدولة المرتبطة.
